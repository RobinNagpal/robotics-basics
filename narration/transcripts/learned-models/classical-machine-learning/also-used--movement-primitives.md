Movement primitives. This page explains movement primitives, which are small learned models of one smooth motion, such as pouring from a jug or wiping a table, taught by showing the motion a few times. It covers the two most used kinds. A dynamic movement primitive is a spring that pulls the hand to a goal, plus a learned shape. A probabilistic movement primitive is a mean path with a spread, learned from several demonstrations. The page answers four questions, and the sections below take them in turn. How does each one work? How do they adapt when the target moves? How are they trained? And when are they a better choice than a neural network policy?

It is for a reader who understands what a model is and how a model learns. It also helps to know about mixture models and hidden Markov models, which learn a motion in a different way. Before this page, it helps to understand trajectory generation, which explains what a trajectory is, why a motion must start and stop smoothly, and how a controller follows the targets a movement primitive produces. Every number on this page comes from a real run of a diagram script. The demonstrations are simulated, but the methods themselves are real, and they are written in NumPy.

The first section gives the idea in one sentence. A movement primitive stores the shape of one demonstrated motion in a few dozen numbers, in a form that still reaches a new goal, can run faster or slower, and can be told to pass through a chosen point. For example, you learn to sign your name once, and after that you can sign it large on a poster or small on a form, quickly or slowly, and start it anywhere on the page. The shape stays yours, because you did not learn a new signature for each size. A movement primitive does the same for a robot arm's motion. A demonstration, here, is one recording of a person doing the motion. The usual way to record one is hand-guiding, also called kinesthetic teaching, where a person switches the arm into a mode in which it gives way to their hands, takes hold of it, and moves it through the motion. The arm records its own joint angles and hand position as it goes, so no camera is needed.

The next part explains dynamic movement primitives, which are made of a spring and a shape. A dynamic movement primitive, or DMP, was introduced by Auke Ijspeert, Jun Nakanishi and Stefan Schaal in the early two thousands. It describes the motion of each number, such as the hand's height, with two parts, which are a spring and a learned shape. For example, this page uses pouring, where a person hand-guides the arm to lift a jug from the table, carry it up and over, and stop with the spout above a bowl. The recording lasts two seconds, with one hundred readings a second, and it gives the hand's forward position and height.

Imagine the hand tied to the goal with a spring, and with a damper so that it does not bounce. Let go, and the spring pulls the hand to the goal and the hand stops there. So the motion is smooth, and it always ends at the goal, wherever the goal is. In a DMP the spring is not tied straight to the goal, because it is tied to an anchor that starts at the hand and slides towards the goal as the motion goes on. This makes the start gentle, instead of a sudden pull. The damper is then set to the value that stops the hand as fast as possible without overshooting. The script uses a spring stiffness of 156.25 and a damping of 25, which are the usual values. The spring alone gives a straight line to the goal. But that line would pour into the bowl by dragging the jug through the bowl's rim.

The spring gives the wrong path on its own, so the second part is a shape term, which is a learned extra push that bends the path away from the straight line. In this version it moves the spring's anchor up, down, forward or back at each moment. The shape term is not written as a function of the clock, because it is written as a function of a phase, which is a number that starts at one and falls smoothly towards zero as the motion goes on. The shape term is made of thirty small bells spread along the phase, and each bell has one learned height. So at any moment the shape term is a blend of the bells near the current phase, multiplied by the phase itself. Multiplying by the phase is the key idea. At the start the phase is one, so the shape term has its full effect, while at the end the phase is close to zero, so the shape term has almost no effect and only the spring is left. And the spring always ends at the goal. So a DMP always reaches its goal, whatever shape it learned.

A diagram shows a straight spring path, the demonstration, the DMP replay, and the learned shape term over time. The blue DMP replay lies almost exactly on the grey demonstration, and the largest gap between them is 5.1 millimetres. The learned shape term is large in the first second, where the arc is, and it fades to nothing by the end.

The thirty heights are the only learned numbers, and a DMP needs only one demonstration to find them. Training works in three steps. First, record the motion, and work out its speed and acceleration at each reading, from the differences between readings. Second, at each reading, work out how much extra push the spring would need to produce exactly that acceleration, because this is the shape the model must learn. Finally, for each of the thirty bells, fit one number, which is a weighted average of that needed push, counting most the readings where that bell is strongest. This is locally weighted regression, with one small fit per bell, and it takes a fraction of a second. So the result is thirty numbers per axis, sixty in all, plus the start, the goal and the duration.

Now move the bowl, give the DMP the new goal, and run it again, because nothing has to be retrained. The page shows a diagram of four goals reached with one learned shape, and the same motion slowed down by changing one number. The same sixty numbers produce four paths, and each one lifts, arcs over and comes down to its own goal. A table lists the goals and how close the DMP gets to them. For example, the demonstration's goal is 40 centimetres forward and 18 centimetres high, and the DMP ends 1.05 millimetres from it, with a highest point of 29.1 centimetres. If the goal is moved to 48 centimetres forward and 24 centimetres high, the DMP ends 0.27 millimetres away, and the highest point rises to 33.6 centimetres. Every run ends within 2.3 millimetres of its goal, and the small leftover comes from the shape term, which is small but not exactly zero when the run stops. The diagram also shows time scaling, because a DMP has one number for its duration. Change it from two to three seconds, and the same motion runs one and a half times slower, while the path stays the same to within 2.1 millimetres. On an arm this is useful for a first slow try, or for slowing down near a person.

The next section covers probabilistic movement primitives, which are a path with a spread. A probabilistic movement primitive, or ProMP, was introduced by Alexandros Paraschos, Christian Daniel, Jan Peters and Gerhard Neumann in 2013. Unlike a DMP, it learns from several demonstrations rather than one, and it keeps not only the typical path but also how much the demonstrations varied at each moment. The word probabilistic means that it describes the chance of each possible path, and not only one path. For example, a person hand-guides a cloth across a table in one wiping stroke, eight times over. Each stroke swings sideways and comes back, but no two are the same. The script records the sideways position of the cloth at one hundred moments in each stroke, with time written from zero at the start to one at the end.

To get from demonstrations to a mean and a spread, first describe each demonstration with a few numbers, by placing ten bells along the time axis. Then find the ten heights that, when the bells are blended, best match the demonstration. This is an ordinary least-squares fit, and the largest mismatch over all eight strokes is 5.8 millimetres. Now each demonstration is ten numbers, so take the average of the eight sets, and that average is the mean path. Then work out how the ten numbers vary together across the eight sets. This is their covariance, which is a table that says how much each number varies and which numbers tend to go up and down together, so it holds the spread. 

A diagram shows the eight wiping strokes, their mean path, and a band two standard deviations wide either side of the mean, so about 95 in 100 paths fall inside it. At the start the spread is 2.0 millimetres, because every stroke starts in the same place. Half-way through, the mean is 11.9 centimetres out, with a spread of 23.9 millimetres, and at the end the spread is 14.5 millimetres. The spread tells the robot two things. Where the band is narrow the demonstrations agreed, so that part of the path probably matters, while where the band is wide the person did not care much, so the robot can bend the path there. Some controllers use this to hold the arm stiffly where the band is narrow and softly where it is wide.

The spread says where the path may bend, and a via-point says where it must not. A via-point is a point that the path must pass through at a set moment. Suppose a cup stands on the table, and the cloth must reach 15.5 centimetres out half-way through the stroke in order to wipe around it. A ProMP answers this with conditioning: of all the paths the demonstrations allow, keep only those that pass through the via-point, and describe what is left. This is a short sum with the mean and covariance, with no retraining at all. It uses the same kind of update as the Kalman filter explained in the programming techniques book, treating the via-point as one very precise measurement. 

A diagram shows the grey band before the via-point, and the narrower blue band of paths that pass through it. Before conditioning the mean at half-way is 11.9 centimetres, and afterwards it is 15.52 centimetres, with a spread of only 1.47 millimetres there. Six paths drawn at random from the conditioned model all pass through the point. The new path does not simply jump to the point and back, because it bends smoothly, in the way the demonstrations varied, since the covariance says how each part of the path moves when another part does. The start and end spreads stay almost as they were, at 1.8 millimetres and 14.4 millimetres. A DMP can also reach a new goal, but it has no natural way to add a via-point in the middle. A ProMP instead can take any number of via-points, and a new start or goal is just a via-point at time zero or one.

The next section explains how they are trained, and what the recordings must be like. A DMP needs one demonstration of the motion, and several can be averaged, although one is normal. It must start and end at rest, and it should be smooth, because the training uses the acceleration, and a shaky recording has a shaky acceleration. So people usually smooth the recording first, and training then takes well under a second. A ProMP needs several demonstrations, usually five to twenty, of the same motion with some natural variation. With too few of them the covariance is poor, because with eight demonstrations and ten numbers each, the spread is only a rough guess. The demonstrations must be lined up in time, usually by scaling each to run from zero to one. If people paused at different moments, a method called dynamic time warping can stretch the recordings so matching parts line up first. Both learn each axis, or each joint, separately in their simplest form. But a ProMP can also learn how the joints vary together, by putting all the joints' numbers into one covariance. Both kinds are usually learned in the hand's position, so that a new goal from a camera can be given in metres. They can also be learned in joint angles, when the arm's pose during the motion matters.

The page then lists where they are used on a robot arm. First is pouring. A person hand-guides a pour once, then a camera finds the cup and the DMP is run with the cup's position as its goal, so the arc over the rim comes along for free. Second is wiping and polishing. A ProMP learns a stroke from several demonstrations, and a via-point then moves the stroke around an object on the table. The spread also tells a compliant controller where it may give way. Third is reaching a moved target. A reach-and-place learned as a DMP adapts at once when the target moves, even during the motion, because the goal can be changed while the DMP runs. Fourth is joining motions into a task. A task is often written as a finite state machine that runs one primitive after another, such as reach, grasp, lift, pour, and put back. Each primitive is taught separately. Fifth is improving by practice. Because a DMP is only a few dozen numbers, a robot can try small changes to those numbers and keep the ones that do better. This is a small, fast form of reinforcement learning. It was one of the early successes of robot learning, for example for ball-in-a-cup games. Finally, two arms together. A ProMP over both arms' positions learns how they move together, so that when one arm is told where to go, the other adjusts.

The next section compares primitives to a learned policy. The obvious competitor for all these jobs is a neural network. The movement chapter of this book describes behaviour cloning, which is a neural network that watches the camera and chooses the next move, trained on many demonstrations. Movement primitives and behaviour cloning both learn from demonstrations, but they suit very different jobs. A table compares them. For the number of demonstrations, a DMP needs one, and a ProMP needs five to twenty, while behaviour cloning usually needs fifty to several hundred. A primitive does not need a camera, because the goal can come from anywhere, but a policy usually needs a camera as its main input. During the motion, a primitive reacts only to its goal, via-points and timing, whereas a policy reacts to anything the camera sees. A primitive models one smooth motion, while a policy models a whole task with many steps. Training a primitive takes under a second on a laptop, but a policy takes hours on a graphics card. You can check a primitive before it runs by computing the whole path first, but you cannot check a policy because it decides each move as it goes. Finally, a DMP always reaches its goal, but a policy only reaches it if the training taught it well. 

Primitives win when you have few demonstrations, the motion is a single smooth movement, and the only thing that changes is where it starts or ends. For example, pouring into a cup at a known place, wiping a stroke, or placing a part all fit that description. They also win when you must check the path before running it, or when you have no graphics card. But a policy wins when the robot must react to what it sees during the motion, such as a towel that folds differently each time, a drawer that sticks, or an object that slides. It also wins for long tasks with many steps and choices, where writing a state machine of primitives would be long and fragile. And it wins when the task has more than one good way to do it, and the camera must decide which. So the two are often combined, where a seeing model or a policy chooses the goal and a primitive then produces the smooth motion to reach it.

The next section explains what goes wrong. A DMP generalises well only near its demonstration, so for a goal far away, or in a very different direction, the shape can look odd. The arc is added exactly as it was learned, and it is not rotated or stretched to suit the new direction, which is why the 36 centimetre, 26 centimetre goal mentioned earlier already arcs up to 35.1 centimetres. Some versions scale the shape by the distance to the goal, which fixes some cases and causes others, because when the start and goal are at almost the same height, the scaled arc shrinks to nothing. So the usual fix is to record demonstrations for the range of goals you need, or to learn in a frame attached to the target. A DMP also does not know about obstacles, because the shape clears the bowl's rim only since the demonstration did. Extra repelling terms can be added near known obstacles, but for real collision checking a planner is needed. A shaky demonstration gives a shaky replay, because the shape is learned from the acceleration, and differences of noisy readings are very noisy. So smooth the recording first. A ProMP's spread is only as good as its demonstrations, because with few of them the covariance is a rough guess and conditioning can give strange paths. In particular, a via-point far outside the band forces the model to use shapes that it never saw. Neither kind checks the joints' limits, because a DMP run with a short duration or a far goal can ask for more speed than the joints allow. Trajectory generation limits and a safety check are still needed underneath. Orientation needs care, because the hand's turn cannot be learned as three separate angles without odd results near some poses. So DMP versions exist for turns written as quaternions, and most libraries include one.

The next part lists the libraries you might use, rather than writing a DMP yourself. The most complete Python package is movement_primitives, from DFKI, by Alexander Fabisch. It provides DMPs, including a version for the hand's position and turn, and ProMPs. Another Python library is pydmps, which provides discrete and rhythmic DMPs. It is small and easy to read, making it good for learning. Finally, dmpbbo is written in C++ and Python. It provides DMPs, plus black-box optimisation to improve them by practice, and is aimed at practice on real robots. But the methods are also short enough to write yourself, as the diagram script shows, because each of them is a few dozen lines of NumPy.

The page then summarizes why to use movement primitives, and what they cost. The libraries make both kinds cheap to try. A movement primitive is a small model of one smooth motion, learned from one or a few demonstrations, where a DMP is a spring to the goal plus a learned shape and a ProMP is a mean path with a spread. What they do for you is let you teach a motion by hand-guiding it once or a few times. The motion reaches a new goal without retraining, can run faster or slower, and, for a ProMP, can pass through a new via-point. Training takes less than a second, and the whole path can be computed and checked before the arm moves. The obvious alternative is a behaviour cloning policy, which needs many more demonstrations and a camera but reacts to what it sees. The other obvious alternative is to write the path by hand as waypoints. That needs no demonstration at all, but someone must be able to say where the path goes. What primitives cost is that each primitive is one motion, so a task needs several primitives and written code to join them. They react only to the goal, via-points and timing, and not to anything the camera sees during the motion. They also do not avoid obstacles or check joint limits. And they generalise only to goals near the demonstrated ones.

The next section discusses the written alternative. Trajectory generation does the same job with no learning at all. Someone writes down a few waypoints, such as "lift to 25 centimetres, move over the bowl, lower to 18 centimetres", and the generator joins them with a smooth curve that obeys the joints' limits. For a new goal, the program simply moves the last waypoints. The written way wins when the path is easy to describe, such as a lift, a straight move and a lower, because it obeys the limits by design and can be read by anyone. The primitive wins when the motion is easier to show than to describe, such as the exact curve of a pour or the swing of a wiping stroke, and when a ProMP's spread is useful. When the path must also avoid obstacles, trajectory optimisation finds a smooth path that keeps clear of them. So some methods start that optimisation from a primitive's path, and the result then stays close to the demonstration.

The final section shows how to use it in Python. It shows the code calls in the most complete library, the DFKI movement_primitives package, so that you can learn a primitive from a recording and play it back to a new goal. The package is installed with pip, and it also needs pytransform3d for the version that handles the hand's turn. The code creates a DMP, giving it the number of dimensions, the execution time, the time step, and the number of weights per dimension. It calls an imitate function, passing in the recorded times and positions, to learn the shape. Then it calls a configure function with the start and the new goal. Finally, it calls an open-loop function to play it back. For a ProMP, the code creates the model, calls imitate with lists of demonstrations, and then gets the mean path and the variance around it. It can also call a condition_position function, passing in a via-point and a time, to get a new ProMP whose paths all pass through that point. 

The configure call is the useful property of a DMP, because you learn the shape once from one demonstration and then ask for a different goal without recording anything new. The condition_position call is the via-point, and it returns a new ProMP, which is why the result is assigned to a new variable rather than changing the original in place. The library gives you the parts that are tedious to get right, like the phase variable, the regression, the numerical integration, and the probabilistic algebra. What you have to collect is the demonstration, and for a ProMP several demonstrations of the same motion. They must be resampled onto a common time vector, because the imitate function pairs each recorded position with a matching time. You should also smooth the recording first, because the shape is learned from the acceleration. What you have to decide is the number of weights and the execution time. More weights follow the demonstration more closely, so they also copy more of whatever shake is left in it, while too few smooth away the part of the motion that mattered. The execution time sets how long the playback takes, and changing it slows or speeds the whole motion without changing its shape. If you would rather see the arithmetic than use a library, each method is just a few dozen lines of NumPy.
