Grasp quality models. 

This page is about grasp models that do not propose grasps at all, because something else proposes the grasp and the model only judges it. A grasp quality model looks at one proposed grasp and gives back a single number, which is how likely that grasp is to hold. The robot therefore tries many possible grasps this way and keeps the one with the best number.

The page answers several questions in turn. It explains why you would split proposing a grasp from scoring it, what a quality model takes in and gives back, and how it works inside. It also covers where the millions of training examples come from, which real models do this, what goes wrong with them, and what they cost you. The page is written for a reader who has already read the grasp models overview, and it builds on concepts from top-down grasp detection, six-degree-of-freedom grasps, and how a model learns.

The first section explains what a grasp quality model actually is. Because it only judges grasps, it takes one proposed grasp and gives back the chance that the grasp will hold. Think of choosing a melon at a market, where you do not know in advance which melon is the best one. You pick one up, press it, smell it, and give it a mental mark. Then you pick up the next one and do the same. After six melons, you buy the one with the best mark. A grasp quality model does the marking, while ordinary code does the picking up. That is because the code proposes grasp after grasp and asks the model to mark each one.

Each half of this split has a name of its own. The code that proposes grasps is the sampler, and the grasps it makes are candidates, which are possible grasps that nobody has checked yet. The quality model is the scorer, and it is sometimes called an evaluator or a critic instead. 

The first diagram on the page shows five candidate grips on a mug seen from above, each with a score from the model. Beside them, the same five scores are sorted from best to worst, so the ordering is easy to see. The arm tries only the top one, which closes across the mug's body. The scores are made up for this drawing, so only their order means anything.

The next part of the page details what goes in and what comes out. Because the sampler and the scorer are separate, the scorer has to be told what the sampler already knows, so its input has two parts. The first is what the camera sees, usually a depth picture or a point cloud of the scene. The second is one candidate grasp, such as a position, an angle, and how deep the jaws go. 

The output is a single number between zero and one. In other words, that number is the model's guess at the chance that this grasp will hold the object when the arm lifts it. A number used in this way is called a probability. So zero means certainly not, one means certainly, and zero point eight seven means eighty-seven times out of a hundred. Because the model is run once for each candidate, a sampler that proposes two hundred grasps makes the model run two hundred times. Those two hundred runs can happen one after another, or on all two hundred together in one batch.

Moving on to how it works inside, the page opens up the scorer to look at its design. The best-known design is Dex-Net's grasp quality convolutional neural network, and it works in four steps. First, code cuts a small square out of the depth picture, centred on the candidate grasp's centre. Second, code turns the square so that the grasp's jaws sit at its left and right edges. This means every patch the network sees is lined up the same way, so the network never has to learn what a grasp at thirty degrees looks like as a separate case. Third, a small convolutional neural network reads the turned patch, and it is given one further number as well, which is how deep the gripper would go. Finally, the network ends with a single output, which is the chance that the grasp holds.

A diagram illustrates this process. It shows a candidate on the depth picture, and the patch cut out around it and turned so the jaws sit left and right. Then a small network reads that patch and gives one number out. 

The second step is the clever part, because turning each patch removes the angle from the problem altogether. The network then only has to learn one thing, which is whether the shape lying between two jaws, lined up left and right, can be held. Quality models for six-degree-of-freedom grasps work the same way, except that they start from a point cloud rather than a depth picture. Code takes the points that lie between the gripper's fingers, turns them into the gripper's own frame, and passes them to a point cloud network.

Because a quality model is only as good as the candidates it is given, the sampler matters as much as the scorer does. Three kinds of sampler are common, and any of them can feed the same scorer. The simplest sampler picks at random and then checks the geometry, finding pairs of points on the object's edge that face each other so both jaws would press straight in. A better sampler refines the best candidates instead of stopping after one round. It samples some candidates, scores them, and then samples new candidates near the best ones. After a few rounds, the candidates gather around the best grasp, and this way of searching is called the cross-entropy method. Finally, the candidates can also come from another model, where a six-degree-of-freedom grasp model proposes the candidates and the quality model then re-scores them.

The page then explains how the model is trained. Because the network has to learn its scores, it needs examples. Every example is a picture, a grasp, and a label, where the label is one if the grasp held and zero if it did not. There are two ways to get those labels, and they cost very different amounts. A diagram shows these two routes. On the left, physics formulas judge grasps on a 3D model, and the computer draws a depth picture. On the right, a real arm tries each grasp, lifts it, and checks what happened. Both routes give the same kind of example: a picture, a grasp, and a one or a zero.

The first route is calculating labels on 3D models. This is how Dex-Net was trained, and it is the cheaper route because it never touches a robot at all. You collect thousands of 3D models of objects and place many candidate grasps on each one. For each grasp, you compute a quality metric, which is a number from physics formulas that says how much push or twist the grasp can resist before the object slips. You repeat the calculation many times with small random changes, such as moving the object a little, offsetting the gripper, or lowering the friction. You then average the results. A grasp that still holds after all these small changes is called robust, so the label is one when the average is high enough. Finally, you draw a depth picture of the object from a virtual camera, with added noise. This way is cheap and fast. Dex-Net 2.0 was trained on 6.7 million examples made like this, with no robot involved.

The second route is trying grasps on a real arm. Instead of speed, this route buys real results by letting real arms try grasps for weeks. The arm looks at a bin, picks a grasp, and tries it. It lifts and checks whether anything is held, using a camera or the gripper's finger position to find the answer. The picture, the grasp, and the result are saved. Then the arm drops the object back in the bin and tries again, day and night. Google's arm farm used this route, and between six and fourteen arms made more than 800,000 grasp attempts to train one quality model. Its labels are real, so there is no gap between simulation and reality, but collecting them is very slow and very expensive.

Next, the page lists well-known models produced by both training routes. Dex-Net 2.0 and its network score top-down grasps on depth pictures using synthetic examples, though its licence allows only education, research, and not-for-profit use. Pinto and Gupta's self-supervised grasping let a real robot collect its own labels by trying grasps for hundreds of hours, meaning no person had to mark anything. Levine and others' hand-eye coordination network is the Google arm farm just mentioned, where the network scored how likely a small movement of the gripper was to end in a good grasp. QT-Opt, also from Google, learned a quality score for arm movements from more than 580,000 real grasp attempts using trial and error. Finally, GPD and PointNetGPD both score six-degree-of-freedom candidates taken from a point cloud, sampling their candidates with geometry first. Most six-degree-of-freedom models also contain a scorer inside them, so this split is common even when you cannot see it from the outside.

To make this concrete, the page provides a worked example of a mug on a table. A depth camera looks down on the mug, and the arm has a parallel-jaw gripper. First, the camera takes one depth picture. Second, the sampler finds pairs of edge points on the mug that face each other, and makes one hundred candidate grasps. Third, for each candidate, code cuts out a patch, turns it, and passes it together with the gripper depth to the quality model, which gives back one hundred scores. Fourth, the sampler makes one hundred new candidates near the ten best, and the model scores those too, repeating this three times. Fifth, code drops any candidate the arm cannot reach, or that is wider than the gripper opens. Sixth, the arm tries the candidate with the highest score that is left, which on this mug is the grasp across the body. Finally, if the grasp fails, the arm tries the next one down the list, and it does not need to run the model again unless the mug moved.

The following section covers what goes wrong when a quality model meets objects it was not trained on. Five things can happen. First, it inherits the formula's blind spots. A model trained on calculated labels has only learned to copy a physics formula, so wherever that formula is wrong, the model is wrong in exactly the same way. Second, it can only pick from what it is shown. If the sampler never proposes the best grasp, the model cannot choose it. Third, it is slow when there are many candidates, because each candidate needs its own run of the network. Fourth, it can be sure and wrong. A high score is a guess, not a promise, and on an unfamiliar shape, it may give a high score to a grasp that fails. Finally, it knows nothing about the task, scoring only whether the object stays in the gripper. People reduce these problems by using a good sampler, mixing a few real robot attempts into the calculated training data, and adding their own checks for reach, collisions, and task rules after the model gives its scores.

The page then asks why you would choose this kind of model, and what it costs. What it does for you is choose well among many options, and it lets you control which options exist at all. Because you write the sampler yourself, you can limit the candidates to grasps that suit your arm, your gripper, and your task before the model ever sees them. The obvious alternative is to compute the quality metric directly using physics formulas, but those need a full 3D model of the object and its exact position. A quality model needs only one noisy depth picture of an object it has never seen. The other alternative is a model that generates good grasps directly. Those are faster, so a separate scorer earns its extra time only when you want to control the candidates yourself, or when you want a second opinion on another model's grasps. What it costs you is time and training data, because scoring hundreds of candidates takes longer, and the training data needs either thousands of 3D models or weeks of real robot time.

The written alternative section notes that you can use written code instead of a learned model. Physics formulas can compute how much push or twist a grasp can resist, and an antipodal test can check that the two contacts face each other. The formulas win when you have a full 3D model of the object, while the quality model wins when you have only a noisy depth picture.

The final section is about using it in Python, treating the scorer as a thing on its own where you bring the candidates and the model tells you how good each one is. It looks at the code for Dex-Net's network, which comes from the gqcnn repository. The code sets up the scorer by loading a configuration file and creating a quality function. It then builds a list of candidate grasps, where each candidate is given a position, an angle, a depth, and the gripper's width in metres. Finally, it passes the camera state and the candidates to the quality function, which returns one score per candidate as a list of floats between zero and one.

The library handles the crucial step of cutting and rotating the image patches for you. If you fed the network a whole picture instead, the numbers would be meaningless. Because a scorer with no candidates does nothing, you have to supply the candidates yourself, either by writing a sampler, using one from the repository, or taking the output of a generator. You also have to supply your own gripper's width. 

You must decide on your cut-off score and your search method. Because scoring is not free, the full Dex-Net policy uses the cross-entropy method to score a batch, keep the best few, sample more candidates near them, and repeat. The costs of using this code include relying on an older version of TensorFlow and a licence limited to non-commercial use. There is also one cost specific to quality models: the score is calibrated against the way the labels were made. For Dex-Net 2.0, that was a physics simulation with assumed friction and an assumed gripper. A score of zero point eight does not mean the grasp succeeds eight times in ten on your arm; it means the simulated gripper succeeded that often. You have to measure the real success rate against the score yourself, on your own objects, before the number is worth anything as a threshold.
