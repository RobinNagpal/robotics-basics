The page is about nearest-neighbour search. It explains how to find the point in a set that is closest to a given point. It answers four questions: how you find the nearest point without measuring the distance to every point, what a k-d tree is and how it is built and searched, what the k-nearest and radius versions of the search are for, and where a robot arm uses all of this. You do not need an algorithms course to follow it, because every step is shown with a small example on a table top. Nearest-neighbour search is the most used technique in this chapter, because other methods, like iterative closest point and assignment and matching, both call it.

The first section gives the idea in one sentence. Nearest-neighbour search finds the point in a set that is closest to a given point, and a k-d tree makes that fast by cutting space into boxes, so that most boxes can be skipped without looking inside them. The given point is called the query, and "closest" usually means the ordinary straight-line distance, which is called the Euclidean distance. For two points on a table at x one, y one, and x two, y two, that distance is the square root of x one minus x two, all squared, plus y one minus y two, all squared. Think of an everyday example where you are in a strange town and want the nearest chemist. You could look up the address of every chemist in the country and work out how far each one is, but nobody does that. Instead, you look only at the part of the map around you, because a chemist in another town cannot be the nearest one. This is what a k-d tree lets a computer do: it looks only at the parts of space that could hold the answer.

The next part of the page explains how it works, step by step. It works the idea through on a table that is 600 millimetres wide and 400 millimetres deep, seen from above. Eleven objects stand on it, named A to K, and the gripper tip is above the table at an x of 430 and a y of 300. The question is which of those eleven objects is nearest to the gripper. The page shows a table of the objects' positions. For example, object A is at 60, 300, and object K is at 220, 40. The example is flat, with two numbers per point, so that it fits on a page. While a point cloud from a depth camera has three numbers per point, x, y, and z, every step works the same way in three dimensions, so nothing is lost by drawing the example flat.

The simplest way to answer the question is to measure the distance from the query to every point and keep the smallest. This is called brute force, because it uses no cleverness, only work. A diagram shows the gripper measuring its distance to every object. Object G, at 400, 270, is nearest, and its distance is the square root of 30 squared plus 30 squared, which is 42.4 millimetres. Then comes H, the second nearest, at 50.0 millimetres. Brute force is always right, and for eleven points it is also fast, because it needs one distance check per point. The trouble starts when there are many points and many queries. For example, matching every point of one three-thousand-point scan to its nearest point in another needs nine million checks.

Those nine million checks are what a k-d tree avoids, because it is a way of storing points so that a search can skip most of them. The name is short for k-dimensional tree, in which k is the number of coordinates each point has. That is two on this flat table, and three for a point cloud. The tree is built by cutting the space in two, again and again. First, you sort the points by x and take the middle one, then draw a line through it across the x direction, so that every point with a smaller x goes to the left side and every point with a larger x goes to the right side. Second, on each side, you sort the points by y, take the middle one, and cut across the y direction through it. Finally, you keep going, switching between x and y at each level, until every point has its own cut. 

For the table, the first step sorts the eleven points by x, and the middle one is E at an x of 300. That is why the first cut is the line x equals 300. Five points go to the left side, and five go to the right side. The second step then works on each side. On the left, sorted by y, the middle point is C, so the left side is cut at y equals 220. On the right, sorted by y, the middle point is J, so the right side is cut at y equals 240. After that, the third level cuts by x again, and so on. A diagram shows the table cut into boxes on the left, and the same cuts drawn as a tree on the right. Each circle in the tree is one point, and it owns one cut. Its left branch holds the points on the smaller side of that cut, and its right branch holds the points on the larger side. E is at the top, because it made the first cut, and the tree is four levels deep. Building the tree takes some work, because each level sorts the points, but it is done once, and after that every search uses the same tree.

Once the tree is built, the search walks down it towards the query and then walks back up again. On the way back, it only looks at a box if that box could hold something nearer than the best point found so far. For the gripper at 430, 300, the search starts by checking E. The distance is 198.5 millimetres, which is the best so far, and the gripper's x of 430 is more than E's 300, so it goes to the right branch. Next it checks J, finding a new best of 125.3 millimetres, and goes to J's upper branch. Then it checks H, finding 50.0 millimetres, and goes to H's left branch. Finally it checks G, finding 42.4 millimetres. G has no branches, so the walk down is over. 

Now the search walks back up and asks, at each cut, whether the other side is worth a look. At H, the other side is empty. At J, the other side is everything below y equals 240. The gripper is at y equals 300, so anything below that line is at least 60 millimetres away. Since the best so far is 42.4 millimetres, nothing on that side can beat it, and the points there are skipped without measuring them. At E, the other side is everything left of x equals 300, which is at least 130 millimetres away, so all five points there are skipped too. The answer is G at 42.4 millimetres, the same as brute force, but the search measured four distances instead of eleven. A diagram shows the order of the checks and the boxes that were skipped. A dashed circle represents the radius of the best distance found. Since a grey box lies wholly outside that circle, it cannot hold anything nearer than the point already found. The saving grows with the number of points. Matching every point of a three-thousand-point scan to a second scan took about forty-four thousand checks with the tree, against nine million by brute force. As a rule of thumb, a search in a well-balanced tree checks a number of points that grows like the number of times you can halve the total, not like the total itself.

The search described so far returns a single point, but two variants of it are used just as often. K-nearest-neighbour search returns the k closest points instead of one. The walk through the tree is the same, except that it keeps a list of the k best points found so far, and skips a box only if the box is further away than the worst of those k. Radius search returns every point within a set distance of the query, for example every point within 40 millimetres. As a result, it skips a box only if the box is further away than the radius. The two answer different questions, and a diagram shows the difference on a cloud that is crowded on the left and thin on the right. In the crowded patch, a 40-millimetre radius holds 88 points, and the 8 nearest points all lie within 10.9 millimetres. In the thin patch, the same radius holds no points at all, and the 8 nearest points reach out to 83.6 millimetres. So, use k-nearest when you need a fixed number of points, for example to fit a plane through. Use a radius instead when the distance itself means something, for example to say that points closer than 5 millimetres belong to the same object.

The next section lists where this is used on a robot arm. First, it finds the surface direction at each point of a cloud. To grip a mug, the arm needs to know which way its surface faces, called the normal. The software takes the twenty or thirty nearest points, fits a flat patch through them, and takes the direction straight out of the patch. Second, it grows clusters of points into objects. A radius search groups every point with the points within 10 millimetres of it, and those groups with their neighbours, until each group is one object. Third, it removes stray points. A point whose nearest neighbours are all far away is probably floating in the air and can be removed. Fourth, it aligns a model to a scan. Every round of iterative closest point finds the nearest scan point for each model point. Fifth, it matches a detection to a known object. The nearest known object in a stored list is the first guess of what a camera sees. Sixth, it chooses the nearest object to pick, or the nearest free spot to place, to keep each move short. Seventh, it looks up stored answers. Programs might describe a new object with a list of numbers and look up the nearest stored shape. Finally, it checks a planned path for collisions. A motion planner asks how far the nearest obstacle is from many points along the arm, and a k-d tree answers quickly.

In all of those places, nearest-neighbour search is exact and fast, as long as the points have only a few coordinates. The search has limits, though, and the page provides a table of common problems, the signs you see, and what to use instead. First, if the nearest point is still far away, you might see a matched point 50 millimetres away when the objects are 20 millimetres apart. Instead, use a maximum distance to reject any match further than a set limit. Second, if there are many coordinates per point, such as 128 numbers describing a surface patch, the tree search is barely faster than brute force. This is because almost every box is close to the query along at least one coordinate, so almost none can be skipped. Instead, use an approximate search, which is allowed to miss the true nearest point now and then. Third, if the cloud changes every frame, building a new tree takes longer than the searches. Instead, use a voxel grid, which cuts the space into equal cubes, or use brute force on a graphics card. Fourth, if points have very different densities, a fixed radius returns hundreds of points in one place and none in another. Instead, use k-nearest, or a mix of k-nearest and a radius. Fifth, if the coordinates measure different things, like position in metres and colour from 0 to 255, the nearest point is decided almost only by the colour. Instead, scale each coordinate so they are comparable before building the tree. Finally, if there are only a few points and a few queries, the tree takes longer to build than brute force takes to answer. In that case, just use brute force.

You very rarely need to write a k-d tree yourself, because almost every point cloud and maths library has one. The page lists well-known libraries. In Python, SciPy provides a KDTree class which is the easiest start, and scikit-learn chooses between brute force or a tree for you. Open3D provides a KDTreeFlann class in Python and C++, which includes a hybrid search for the k nearest within a radius. In C++, the Point Cloud Library uses k-d trees for normal estimation and clustering. Nanoflann is a fast, small library contained in a single header file. FLANN stands for Fast Library for Approximate Nearest Neighbors, and FAISS is used for millions of points with many coordinates, running on a graphics card. OpenCV also matches image features using brute force or FLANN.

The next section steps back to explain why you would choose a k-d tree and what it costs. It lets the software answer "what is next to this point?" hundreds of thousands of times per camera picture. The obvious alternative is brute force, which is simpler, needs no building step, and is always exact. Brute force is the right choice for a few hundred points or fewer, or for a single query. The tree wins instead when there are many queries against the same set. A second alternative is a voxel grid, which is quicker to build and good when points are spread evenly, but poor when the density varies because the cube size cannot suit both crowded and thin places. The costs of a k-d tree are that building it takes time, so it is only worth it for many queries. A tree built on one frame's cloud is out of date on the next, so a live pipeline builds a new tree every frame. It must be rebuilt if many points change, and it only helps for points with a few coordinates.

The page then asks whether a learned model could take over this hand-written method. No learned model does, because the search gives the exact answer to a plain question, and a network could only guess that answer. Instead, learned models use the search themselves. Point cloud models like PointNet++ collect points within a small distance of a centre, and DGCNN links each point to its nearest neighbours, so both run this search inside the network. The classical k-nearest neighbours learning method is built on it too, predicting by copying the answers of the most similar stored examples.

The page notes several places to read next. Iterative closest point uses nearest-neighbour search in every round to line a model up with a scan. The page on assignment and matching shows why taking the nearest is not enough when two objects compete for one partner. The clustering page uses radius search to group points into objects, and the least-squares fitting page fits a plane through a point's neighbours to get its normal. Tracking and association uses nearest neighbour with a gate to match objects over time.

The final section shows how to use nearest-neighbour search in Python. It focuses on SciPy, which is the easiest to start with, and Open3D, which you will meet inside point cloud code. In SciPy, you pass an array of points to the KDTree class to build the tree once. Then you can call its query function to find the single nearest point, or ask for the k nearest points by setting k to 8. You can also run a radius search using the query ball point function, or combine them by asking for the k nearest but setting a distance upper bound. In Open3D, you pass the point cloud to the KDTreeFlann class. It has functions for k-nearest search, and a hybrid search which finds the k nearest within a radius, which is exactly what normal estimation wants. 

Both libraries do the hard work of choosing splitting planes, building the tree, and pruning boxes. SciPy will even answer a whole array of queries in one call, which is much faster than a Python loop. What you still write yourself is the decision about what to do with the answer, because the tree always returns a nearest point even if it is on the other side of the table. You also write the rebuild step for each new camera picture. Finally, there is one detail that will quietly break programs if you do not notice it. The radius or distance limit is a real distance in the units of your points. However, SciPy returns ordinary distances, while Open3D returns squared distances. So a threshold of 0.02 in SciPy corresponds to 0.0004 in Open3D. Comparing an Open3D result against an unsquared threshold does not raise an error, and it silently accepts neighbours far further away than you meant.
