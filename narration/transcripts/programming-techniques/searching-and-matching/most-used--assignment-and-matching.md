Assignment and matching. This page explains assignment, which means pairing up the things in one list with the things in another list. Each thing gets at most one partner, and the pairs are chosen to be as good as possible overall. On a robot arm, the two lists are often the objects the robot saw one camera frame ago and the objects it sees now. So assignment answers the question "which one is which?" for every object in the new frame.

The page shows two ways to do it, and they do not always agree. Greedy matching takes the best single pair first, then the best of what is left, and so on. The Hungarian algorithm instead finds the pairing with the smallest possible total cost. To show where the two differ, the page works through a small example with real numbers. It then shows how to handle objects that appear and disappear.

It is for a reader who has read about nearest-neighbour search and the chapter overview. Because both methods are explained from the start here, no algorithms course is needed. Book two's page on tracking and association goes further into tracking objects over time, so this page stays with the technique underneath it.

The first section gives the idea in one sentence. Assignment, as the introduction described it, writes down a cost for every possible pair. It then chooses a set of pairs, with no thing used twice, whose costs add up to the smallest total.

The cost is a number that says how bad a pair would be. For matching objects between two frames, the usual cost is the distance between the old position and the new one. A cost can also add in other differences, such as size or colour, so that position alone does not decide the pair.

Here is an everyday example, away from robots. A delivery company has three vans and three parcels, each at a different address. Each van can take one parcel, so the three parcels have to be shared out one to a van. The manager writes down how far each van is from each parcel, and wants the three trips to add up to the least driving. Sending each van to its own nearest parcel does not always work. This is because two vans may have the same nearest parcel, so one of them then has to drive a long way instead. That is why the manager has to consider the three trips together. A problem of that shape is called an assignment problem.

The next part of the page explains how it works, step by step, starting with an example of three mugs on a moving belt. To turn the vans and parcels into a robot problem, picture a camera that looks down at a belt carrying three mugs from left to right. The robot keeps a list of the mugs it knows, with where each was in the last frame. While the robot holds that list, a detector reports three mugs in the new frame, called detection 1, detection 2, and detection 3. Between the two frames the belt moved by about 50 millimetres, and all the positions below are in millimetres.

In the last frame, mug 1 was at coordinates 100, 200. Mug 2 was at 180, 200, and mug 3 was at 400, 150. In this frame, detection 1 is at 150, 200. Detection 2 is at 235, 200, and detection 3 is at 450, 150.

The robot does not know that detection 1 is mug 1, because the detector gives no names, only positions. The first step is therefore to write down the cost of every possible pair. A diagram shows the three mugs one frame ago, the three detections now, and a table of distances. The table has one row per known mug and one column per detection. Each cost in it is the straight-line distance between the two positions.

The table is called the cost matrix, since a matrix is a grid of numbers. Filling it in needs one distance for each pair, so there are three times three, which is nine distances here.

With the cost matrix filled in, the first way to read a pairing out of it is greedy matching. This means repeatedly taking the cheapest pair that is still allowed, until no allowed pair is left at all.

First, the cheapest cost in the whole table is 30.0, so greedy takes mug 2 with detection 1, and both mug 2 and detection 1 are used up and cannot appear in any later pair. Second, the cheapest cost left is 50.0, so greedy takes mug 3 with detection 3, which uses up mug 3 and detection 3 as well and leaves only one pair that is still possible. Finally, only mug 1 and detection 2 are left, so greedy must take that pair, and it costs 135.0, which is far more than either of the two pairs taken before it.

The total is 30.0 plus 50.0 plus 135.0, which equals 215.0 millimetres. A diagram shows this greedy pairing next to the best possible pairing. It shows that the greedy answer is wrong, because it says that mug 2 moved 30 millimetres backwards, against the belt, and that mug 1 jumped 135 millimetres forwards past it. This happened because the first step took the cheap pair of mug 2 with detection 1 without noticing that it left mug 1 with only a very expensive choice. That is the weakness of greedy methods in general. Each choice looks only at itself, not at what it leaves for the choices after it.

Since greedy can go wrong in this way, the obvious repair is to try every pairing and keep the cheapest one. With three mugs there are only three times two times one, which is six ways to pair them up, so trying them all is easy. A table lists the six pairings, with the detection given to each mug and the total cost.

The best total is 155.0 millimetres, which comes from pairing mug 1 with detection 1, mug 2 with detection 2, and mug 3 with detection 3, costing 50.0 plus 55.0 plus 50.0. Each mug therefore moved about 50 millimetres with the belt, and that is what really happened. The greedy answer of 215.0 millimetres is also in the table, which means greedy chose a pairing that is allowed but not the cheapest one.

Trying every pairing is always right, but the number of pairings grows very fast. For n objects it is n times n minus one, and so on down to one, a number called n factorial. So for 10 objects that is over 3.6 million pairings, and for 12 it is over 479 million. That growth is plotted in the chapter overview, and it is the reason a faster method is needed.

The next section introduces the Hungarian algorithm. It reaches the same best pairing as trying every one, but without doing all that work. It was published by Harold Kuhn in 1955, who named it after the work of two Hungarian mathematicians. It is also called the Kuhn–Munkres algorithm, and both names refer to the same method. For n objects it needs roughly n times n times n steps, which is 1,728 for 12 objects instead of 479 million.

It rests on one fact, which is that every pairing uses exactly one number from each row of the cost matrix. So if you subtract the same amount from every number in one row, every pairing's total goes down by that same amount. This means the best pairing is still the best one after the subtraction. The same is true for a column, so the algorithm uses these subtractions to make zeros appear in the matrix without changing which pairing is best. Once it can pick one zero in every row and every column, those zeros are the best pairing, because no pairing can cost less than zero.

For the mugs, with the costs rounded to whole millimetres, it goes in three stages. A diagram shows these three stages side by side, highlighting the zeros that the algorithm picks.

In the first stage, you subtract each row's smallest number from that row, and since those smallest numbers are 50, 30 and 50, mug 1's row becomes 0, 85, 304. In the second stage, you subtract each column's smallest number from that column, where the smallest numbers are now 0, 25 and 0, so only the detection 2 column changes and mug 2's row becomes 0, 0, 245. In the third stage, you look for one zero in every row and every column, and mug 1 must take detection 1 because that is its only zero, which then leaves detection 2 for mug 2 and detection 3 for mug 3.

The answer is mug 1 with detection 1, mug 2 with detection 2 and mug 3 with detection 3. This is the same best pairing that the full search found, with the total 155.0 millimetres from the original costs.

The mug example was settled by those two subtractions alone, but that does not always happen. Sometimes, after the second step, you cannot pick one zero in every row and column. The algorithm then has one more step, which it repeats until you can.

First, cover all the zeros with as few straight lines as possible, drawn through whole rows or whole columns. If you need as many lines as there are rows, then a full set of zeros exists and you are done. If not, find the smallest number not covered by any line, subtract it from every uncovered number, and add it to every number where two lines cross, then go back to the previous step.

The page gives a small example that needs this extra step, where three parts must go into three slots. A table shows the distances the arm travels in millimetres for each part and slot combination. After subtracting each row's smallest number and then each column's smallest number, parts 1 and 2 both have their only zero in slot 2, so there is no full set of zeros yet. Two lines cover every zero: one down the slot 2 column, and one along part 3's row. Since the smallest uncovered number is 10, subtracting it from the uncovered numbers and adding it where the lines cross updates the matrix. Now part 1 takes slot 2, part 2 takes slot 1 and part 3 takes slot 3, and that gives a total of 50 millimetres in all. Trying all six pairings confirms that 50 millimetres is the smallest total these three parts can reach.

You will not usually do this by hand, because libraries do it in a fraction of a millisecond for the tens of objects a robot arm sees. The point of the example is instead to show that the answer is exact, not a guess.

The next part covers lists of different lengths, and the gate. So far both lists have held three mugs, but real frames rarely have the same number of objects in both lists. An object can be hidden by the arm, so it has no detection, and a new object can be put down, so a detection has no old object. Suppose that, in the same frame, mug 3 is hidden behind the arm and a new mug has been put down at the far end of the belt. A diagram shows this case, first without a gate, and then with a gate.

Without a gate, the solver pairs the hidden mug with the new one. It is told to pair all three mugs, and it does so with a total of 324.3 millimetres. That total includes pairing mug 3 with the new mug 219 millimetres away. The algorithm has no way to know that no mug moves 219 millimetres in one frame on this belt, because it only knows that this pairing has the smallest total.

With a gate of 80 millimetres added, where a gate is a largest allowed cost, any pair above it is not allowed at all. Mug 1 and mug 2 are then paired as before. Mug 3 now has no partner, so the robot keeps it in its list and marks it as not seen. The far detection has no partner either, so it becomes a new mug.

A gate is usually added by setting every cost above the gate to a very large number before solving, and then throwing away any pair that still uses one. Most libraries also accept a cost matrix that is not square, with more rows than columns or more columns than rows. They then pair as many as they can, and leave the rest unpaired.

How wide to make the gate is a real decision, because it can go wrong in either direction. Too narrow, and a mug that moved a little faster than expected is lost and then counted again as new. Too wide, and a hidden mug is paired with a newcomer. Book two gives a way to choose the width from the camera's measurement error, in the section on gating.

The page then provides pseudocode to show how all the pieces fit together. The Hungarian algorithm's inner bookkeeping is left to a library, so the code shows only how it is called and how its answer is used.

First, it builds the costs by checking the distance between each old object's predicted position and each new detection. If the distance is greater than the gate, it sets the cost to a very large number. Then, it passes this cost matrix to a Hungarian algorithm library function to get the pairs. It removes any pair whose cost is very large. For the remaining pairs, it updates the old object with the new detection. If an old object has no pair, it marks it as not seen and drops it after several frames. If a detection has no pair, it starts a new object.

The page notes that the predicted position is important, because the belt keeps moving between the two frames. If the robot knows that the belt moves 50 millimetres per frame, it should compare each detection with where the mug should be now. In other words, it should not compare with where the mug was, since the mug has moved since then. With that prediction, every correct cost in the example would be close to zero millimetres instead of about 50 millimetres. As a result, the wrong pairings would stand out far more clearly. The Kalman filter page shows how to make that prediction.

The next section explains where assignment is used on a robot arm. The mugs on the belt are only one use. The same technique appears wherever two lists of things must be paired one to one.

First, following objects from frame to frame. This is the example on this page, matching each detected mug to the mug seen one frame ago, so that the robot keeps a steady name for each object while it plans. Most learned trackers pair their boxes with the Hungarian algorithm in exactly this way.

Second, matching detections to the robot's list of known objects. A robot that keeps a list of objects on the table, with their poses, must decide after each new picture which detection is which listed object.

Third, matching what two cameras see. Two cameras look at the same table from different sides, and after turning both sets of detections into positions in the arm's frame, assignment pairs up the two views of each object.

Fourth, giving each object a place. A robot must put four parts into four slots of a tray, and assignment chooses which part goes into which slot so that the arm travels the least in total, using travel distances or travel times as the costs.

Fifth, sharing work between two arms. Each arm gets some of the objects to pick, so with a cost for each arm-object pair, assignment splits the work between them. If an arm may take more than one object, the problem grows beyond plain assignment, and optimisation solvers take over.

Sixth, matching image features. To find a known object in a picture, a program matches small patches of the picture to patches of a stored image. A simple and common rule keeps a match only if each patch is the other's nearest neighbour, and that rule is called a mutual nearest neighbour check, which is a cheap form of one-to-one matching.

Finally, training a learned detector. The DETR detector is trained by matching each real object to exactly one of the model's answers, and that match is made with the Hungarian algorithm.

The page then discusses where assignment is useful, and where it is not. All of those uses rest on the same guarantee, which is that the Hungarian algorithm always returns the pairing with the smallest total cost. The catch is that the smallest total is only the right answer if the costs are right.

A table lists common problems, the signs you see, and what people use instead. For example, if objects move further between frames than they are apart, names swap between neighbouring objects. The solution is to predict each object's new position first, and compare against the prediction. If an object disappears and another appears, a hidden object might be matched to a new one far away, which is why people use a gate to forbid pairs above a largest cost. If objects look alike and stand close together, names swap when two objects pass each other. You can fix this by adding appearance to the cost, such as colour or size, or by waiting until they are apart. For hundreds or thousands of items, the full cost matrix takes too long to fill in, so people use nearest-neighbour search with a mutual check instead of a full assignment. Finally, if one arm may take several objects, or some pairs must go together, plain assignment cannot express the rule. You need an integer programming solver, such as OR-Tools.

Greedy matching is good enough when objects are much further apart than they move between frames. So on a table with a few objects that stand still, greedy and the Hungarian algorithm give the same answer. Greedy is also simpler to write when there is no library at hand.

The next section lists libraries that provide the algorithm. Since you will not write the Hungarian algorithm yourself, what matters is where to find it ready-made. It, or a close relative that gives the same answer, comes with most maths libraries. A table lists well-known libraries and the functions to look up. For example, in Python, SciPy provides linear sum assignment, which accepts matrices that are not square and is the usual choice. OR-Tools offers solvers for multiple languages including C++ and Java, and also handles larger problems. The munkres library is a small pure-Python version. In C++ and Python, dlib provides max cost assignment, which finds the largest total, so you must pass costs with their sign flipped. Finally, OpenCV provides a brute force matcher with cross check enabled, which does the mutual nearest neighbour check for image features, though this is not a full assignment.

With those libraries in hand, the next section pulls the page together. It answers four questions: what the technique is, what it does for you, why it rather than the obvious alternative, and what it costs.

The Hungarian algorithm takes a table of costs for every possible pair and returns the one-to-one pairing with the smallest total. This means a robot can keep a steady name for each object from frame to frame, and share out work or places in the cheapest way.

There are two obvious alternatives, and each of them falls short. The first is to give each object its nearest detection, which is simple, but two objects can claim the same detection and nothing stops them. The second is greedy matching, which does prevent double claims and is correct when objects are well apart. However, in the mug example it gave a total of 215.0 millimetres against the best 155.0 millimetres, and it swapped two mugs' names. The Hungarian algorithm instead considers all the pairs together, so a cheap pair that forces an expensive one elsewhere is not chosen. Its answer also does not depend on the order in which the objects are listed. Trying every pairing gives the same answer, but only for a handful of objects, because the count of pairings grows as n factorial.

The costs of using it start with the cost matrix itself, which you must fill in completely, one number per pair. That is fine for tens of objects, and far too much for thousands. The answer is also only as good as the costs, so you need a sensible cost and a gate. Choosing the gate's width is then a judgement about your camera and your scene. The algorithm returns a pairing even when every pairing is poor, so the program around it must handle lost and new objects. Finally, it pairs one to one only, so a rule such as "an arm may carry two objects" needs a more general solver.

The next section covers the learned alternative. The previous section named a poor cost as the main weakness, and that is exactly where learning helps. There is no learned model that replaces the pairing step itself, because once the costs are known, the Hungarian algorithm finds the best pairing exactly and quickly. What learning improves is therefore the cost, not the pairing. Book six describes trackers that also compare how the objects look, using an embedding, which is a list of numbers that describes each box. Two look-alike objects that pass close to each other are then less likely to swap names, and a matching step still makes the pairs. SAM 2 works differently. You click once on an object, and it follows the object's outline through a video from its memory of how it looked, with no pairing step. However, it needs a smooth video, and it cannot bridge a gap between separate photos. Position costs and this page's method are enough when objects stand well apart, while learned appearance is worth adding when similar objects cross.
