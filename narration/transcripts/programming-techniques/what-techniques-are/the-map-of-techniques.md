The map of techniques. This book describes thirty-four programming techniques, and they have different names, take in different things, and give back different answers. This page is the map of all of them, because it sorts them into seven kinds, which this book calls categories. For each category, it then says what the techniques do and where to read about them.

It answers three questions. What are the seven categories, and which techniques are in each? Where does each category do its job when one robot arm does one task? And in what order should you read the chapters of this book?

It is for a reader who has read the earlier pages of this chapter, especially the page on programmed, not learned methods. You can also come back to it at any time, when you want to see where one technique fits among the others. Book six has a page with the same shape for learned models, called the map of models.

The next part of the page explains one task and seven kinds of technique. The easiest way to see all seven categories is to follow one task from start to finish. A robot arm has a camera on its wrist, and there are three mugs on a table with a rack of pegs at one end. The task is to find the mugs with the wrist camera and hang each one on the rack.

To do this, the robot must do several separate things. First, it must turn what the camera sees into positions measured from its own base, and it must pick the mug pixels out of the picture and ignore the table. Second, it must find the table top and keep each mug's position steady while the camera moves, and then decide which mug is which from one picture to the next. After that, it must find a path to each mug and on to the rack that hits nothing, and drive its motors smoothly along that path. Finally, it must keep track of the whole job, such as which mug is next, and what to do if a grasp fails.

Each of these jobs is done by a different kind of technique, and those kinds are the seven categories.

The diagram on the page shows this task with a robot arm above three mugs and beside a rack. The seven categories are numbered, and each number sits next to the part of the scene that its techniques work on. These are the camera, the mugs, the table top, the mug pixels, the path to the rack, the joints, and the task list.

A real arm does not always use every technique in this book, and a simple pick-and-place arm may use only six or seven of them. However, almost every arm task uses at least one technique from each of the seven categories.

Moving on to the seven categories themselves. The previous section numbered them on the picture, so this section describes each of them in turn. Inside each chapter, the technique pages are split into two groups. The most used group holds the techniques that nearly every arm program needs, or that matter most when they go wrong. However, the also used group holds techniques that are used often, but only for some tasks or some kinds of arm. So, you should read the most used group of a chapter first. Each category described below names the most used techniques first, and then the also used ones.

The first category is geometry and cameras. These turn pixels, frames, and joint angles into positions you can trust, and four of these techniques are most used. First, the pinhole camera model says which pixel a point in space lands on, and turns a pixel and its depth back into a point. Second, rigid transforms move a position from one frame to another, such as from the camera to the arm's base. Third, calibration measures the numbers that the other two need, which are the camera's own settings, and where the camera sits on the arm. Fourth, pose from points finds where a known object sits from a few of its points seen in one picture, a problem called perspective-n-point. One technique is also used, which is multi-view geometry. This combines pictures taken from different places to find where points are in space. So in the mug task, these techniques turn each mug's pixels into a position the arm can reach. This is covered in the geometry and cameras overview.

The second category is searching and matching. These find the closest thing, and decide which thing is which, and three of these techniques are most used. First, nearest-neighbour search finds the point or object closest to a given one, as in the closest-mug example on the first page. Second, iterative closest point lines up two sets of points, such as a stored 3D model of a mug and a fresh scan. Third, assignment and matching pairs up two lists, such as the mugs seen in this picture and the mugs seen in the last one. One technique is also used, which is image features and matching. This finds the same small spots in two pictures and pairs them up. So in the mug task, these techniques make sure that mug two in one picture is still mug two in the next. This is covered in the searching and matching overview.

The third category is fitting and estimation. These get a clean shape or a steady number out of noisy measurements, and four of these techniques are most used. First, least-squares fitting finds the line, plane, or circle that is closest to many points. Second, random sample consensus, or RANSAC, does the same while ignoring points that are plainly wrong. Third, the Kalman filter combines each new reading with what it already knew, to give a steady estimate of something that may be moving. Fourth, sensor streams covers how to handle readings that arrive one after another from many sensors, at different rates and times. One technique is also used, which is system identification. This measures the numbers inside a physical model of the arm, such as a joint's friction or the mass in the gripper. So in the mug task, RANSAC finds the table top, and a Kalman filter keeps each mug's position steady as the camera moves. This is covered in the fitting and estimation overview.

The fourth category is image and point cloud processing. These clean up and cut up pictures and point clouds so objects stand out, and three of these techniques are most used. First, thresholding and colour masks keep the pixels whose colour or depth is in a chosen range. Second, morphology and the distance transform tidy up those pixels, and find the point most central in a shape. Third, clustering groups nearby points into separate objects. Two techniques are also used. The first of them, edges and contours, finds the outline of each shape. The second, volumetric maps, divides the space around the arm into small cubes and records which ones are full, empty, or not yet seen. So in the mug task, a depth threshold removes the table, and clustering splits the remaining points into one group per mug. This is covered in the image and point cloud processing overview.

The fifth category is planning and search. These find a way for the arm to get from here to there without hitting anything, and three of these techniques are most used. First, sampling-based planning tries random arm poses and joins the safe ones into a path. Second, numerical inverse kinematics finds the joint angles that put the gripper at a chosen pose. Third, trajectory optimisation takes a path and makes it shorter, smoother, and further from obstacles. Three techniques are also used. The first of them, graph search, finds the shortest route through a grid or a graph of poses. Second, sampling-based optimisation and model predictive control tries many random plans, keeps the best, and plans again a moment later from where the arm now is. Third, visibility and next best view works out what a camera can see from a pose, and chooses where to look next. So in the mug task, inverse kinematics turns "gripper above mug two" into joint angles, and a planner finds a path to the rack that does not hit the rack itself. This is covered in the planning and search overview.

The sixth category is control and motion. These turn a planned path into smooth, safe motor commands, and four of these techniques are most used. First, proportional-integral-derivative control, or PID control, makes each joint follow its target angle, many times a second. Second, trajectory generation decides how fast to move along the path at each moment, so the arm starts and stops smoothly. Third, arm dynamics works out the torque each joint needs to hold the arm up and to speed it up, so the controller does not have to wait for an error. Fourth, safety monitoring checks the arm's limits in software and stops it when one is broken or a person comes too close. One technique is also used, which is impedance and force control. This makes the arm give way when it touches something, and stop if it pushes too hard. So in the mug task, these techniques move the arm to each mug, and let it feel the peg when it hangs the mug on the rack. This is covered in the control and motion overview.

The seventh and final category is decisions and task logic. These decide what the robot does next, and in what order, and two of these techniques are most used. First, a finite state machine moves the robot from one named step to the next, such as looking, picking, and hanging. Second, a behaviour tree arranges the steps as a tree, which makes it easier to add retries and fallbacks. Two techniques are also used. The first of them, greedy algorithms and set cover, makes a good choice quickly by taking the best-looking option at each step. The second, optimisation solvers, finds the best order or assignment when the greedy choice is not good enough. So in the mug task, a state machine runs the job, and a greedy rule picks the closest mug next. This is covered in the decisions and task logic overview.

For each technique, it shows its category, whether it is in the most used or also used group, a one-line summary of what it does, and what it does specifically in the mug task.

Of the thirty-four pages listed, twenty-three are in a most used group and eleven are in an also used group. A few of these do the same job in two ways. For example, finite state machines and behaviour trees both run the task, least squares and RANSAC both fit shapes, and graph search and sampling-based planning both find paths. So the page on choosing a technique explains how to pick between them, and each technique page compares itself with its neighbour.

The next part of the page explains when each kind does its job. The map picture earlier showed where each category works, but it is also useful to see when each one works. The task for one mug can be split into seven steps. First, look from above. Second, find the mugs. Third, choose the next mug. Fourth, plan the reach. Fifth, reach and grasp. Sixth, carry the mug to the rack. And finally, hang it and let go.

The page includes a timeline of these seven steps for one mug, with a coloured bar for each category showing the steps in which it is busy. Reading the timeline from start to finish shows that decisions and task logic run for the whole task, perception techniques are busy at the start, and control is busy from the reach to the end.

At the start, image and point cloud processing and geometry turn the camera's pictures into mug positions. Fitting and searching then tidy those positions and match them to the mugs seen before, and planning works out the reach. After that, control drives the arm for the rest of the task. Geometry and fitting come back during the grasp, because the camera takes a closer look as the gripper comes down. Decisions and task logic run from start to finish, because they decide when every other step begins.

This is one way to build the task, not the only one. For example, a task where the mugs are always in the same place would not need the perception bars at all. However, a task where the arm must avoid people would have planning running during the carry as well.

The next section shows how the categories connect. The seven categories are separate chapters, but the techniques in them depend on each other, because the output of one is very often the input of the next.

First, a threshold and clustering cut the mugs out of the depth picture, and then the pinhole camera model turns each mug's pixels into points. A rigid transform moves those points into the base frame, and RANSAC and least squares fit the table and the mug's rim. Nearest-neighbour search and assignment then keep track of which mug is which, so that a greedy rule can choose the next mug. After that, inverse kinematics and a planner find the joint angles and the path. Then trajectory generation and PID control drive the motors, with arm dynamics supplying most of the torque and safety monitoring watching every command. A state machine or behaviour tree runs all of it in order, and this chain, from picture to motors, is the most common way to build a programmed picking robot.

Many of the categories also share the common building blocks explained earlier in the book. Planning and decisions both use graphs, while fitting, planning, and optimisation solvers all minimise a cost function, and geometry and planning both use transforms. So once you know one chapter, the next one is easier.

The categories also connect to book six, because some steps in the chain are often done by a learned model instead of a written technique. The page includes a table showing the most common swaps between written techniques and learned models. For example, to cut objects out of a picture, you might swap written thresholding and clustering for a learned segmentation model. To find a path, you might swap written sampling-based planning for a learned motion planner. And to decide the steps of a task, you might swap written behaviour trees for a language model acting as a planner.

Even when a learned model takes over one job, the written techniques around it usually stay. For example, a detection model gives only a box in the picture, so the pinhole camera model and a rigid transform still have to turn that box into a position the arm can reach.

The next section helps you find a method by job. Most people come to these books with a job in mind rather than a method, so this section starts from the job instead of the technique. It provides a large table where each row is a job the arm must do. It then lists the page that helps you choose how to do it, the written techniques that can do it, and the learned models that can do it.

For example, if the job is to find an object in a picture, the table points to the object perception page, lists written techniques like thresholding and clustering, and lists learned models like object detection and segmentation. If the job is to choose a grasp, it points to the choosing a grip page, lists written techniques like morphology and least-squares fitting, and lists learned models like six-degree-of-freedom grasps or suction and affordance models.

Most jobs have both a written and a learned answer, and the reference pages say which one suits which case. However, two jobs in the table have only one side. No learned model is in common use to check whether the arm can reach a pose, because inverse kinematics already gives an exact answer quickly. And no written technique can follow an instruction in free wording, because a person can say the same thing in too many ways to list them all. Many real arms therefore mix the two sides, so that a learned model finds the object and written techniques do the rest.

The learned column also includes the methods of the classical machine learning chapter, which are not neural networks. They appear in the rows where the input is only a few measured numbers, such as correcting a sensor, tuning a controller's gains, learning a motion from a few demonstrations, and scoring grasps or spotting faults from logged numbers.

The next part gives a suggested reading order. If you want to read the book through, the chapters are numbered in the order this book suggests. Read them from chapter one to chapter eight. Each chapter explains its own terms, so you can also start anywhere.

The suggested order starts with this chapter, because everything else uses its words, such as technique, parameter, frame, graph, noise, cost, and loop. Next is geometry and cameras, because every other chapter needs positions in the right frame. Third is searching and matching, which finds the closest thing and decides which thing is which. Fourth is fitting and estimation, which turns noisy pixels and points into clean shapes and steady numbers. Fifth is image and point cloud processing, which cuts the objects out of a picture or a point cloud. Sixth is planning and search, which needs positions and shapes from the chapters before it. Seventh is control and motion, which carries out what the planner decided. Finally, the eighth chapter is decisions and task logic, which ties all the others together into a whole task.

Chapters three, four, and five lean on each other, so you can read those three in any order, because each one uses a little of the other two. For example, clustering in chapter five uses the nearest-neighbour search from chapter three, while RANSAC in chapter four is often run on the points that chapter five cut out. And the matching in chapter three often works on positions that a Kalman filter from chapter four has made steady. So whichever of the three you read first, the other two will be easier after it.

If you have one job in mind, you can jump straight to its chapter. For example, if you only want the arm to move smoothly to a known pose, read planning and search, and then control and motion.

The page then suggests where to read next. The geometry and cameras overview is the next chapter in the suggested order. The map of models in book six does the same job for learned models. The page on programmed methods for one arm in book three shows how these techniques are combined into whole systems. And the tools and libraries page in book three shows the software, such as Move It 2, Open C V, and Open 3 D, that provides many of these techniques ready to call.

The final section is about using these techniques in Python. It adds the practical layer, which is the library you would actually import for each of the seven categories. After hearing this, you should be able to look at a job on your arm and know which package to install first.

The page shows a block of Python code with seven import statements, one for each category. It imports Open C V for geometry and cameras, specifically to solve perspective-n-point. It imports K D Tree from SciPy for searching and matching. It imports least squares from SciPy for fitting and estimation. It imports Open 3 D for image and point cloud processing. It imports Move It Py from Move It for planning and search. It imports Ruckig for control and motion. And it imports py trees for decisions and task logic.

Those seven cover the mug task almost completely. Open C V and Open 3 D turn the wrist camera's pictures into mug positions. SciPy's K D Tree and least squares tidy those positions and match each mug to the mug seen in the last picture. Move It Py plans a reach that hits nothing. Ruckig turns the plan into joint commands that respect the arm's speed and acceleration limits. And py trees holds the order of the whole job. The tools and libraries page shows working code for Move It Py and py trees on a six-joint arm.

What the libraries do for you is the hard arithmetic inside each technique, which is why this book explains the steps rather than asking you to write them. What you write yourself is everything between the seven lines. This is the code that carries numbers from one library to the next in the right frame and the right unit, and the code that decides what to do when a step returns nothing. That glue is usually larger than all seven calls together, and it is where the bugs live, because no library checks that the pose you hand to Move It Py is measured from the base rather than from the camera.

What you have to decide first is which of the seven you need at all. As mentioned earlier, a simple pick-and-place arm uses only six or seven of the thirty-four techniques, so importing all seven libraries into one program before you need them buys you trouble. It is real trouble, too, because these packages do not arrive together. Move It Py and Ruckig come with a R O S two installation, while Open C V and Open 3 D come from pip or conda, and two of them in one Python process can insist on different versions of NumPy. Adding one library at a time, and checking the arm still runs after each one, is slower to start and much faster to finish.
