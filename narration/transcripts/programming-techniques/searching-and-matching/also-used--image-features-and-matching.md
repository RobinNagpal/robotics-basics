Image features and matching. 

This page explains how a program finds the same small spots in two pictures, and how it uses those spots to say where a known flat object is. It does that by answering five questions, in the order in which a program answers them. Which spots in a picture are easy to find again? Then how does a program describe one of those spots as a list of numbers? How does it pair each spot in one picture with the right spot in the other? Once it has those pairs, how does it throw away the ones that are wrong? And what can a robot arm do with the pairs that are left?

The page is for a reader who knows what a pixel and a grey picture are, and who understands nearest-neighbour search. That matters here because pairing spots is itself a nearest-neighbour search, carried out on descriptions instead of positions. This page also uses RANSAC, a method that fits a model when some of the data is wrong. 

The work is usually called feature matching, and the word feature needs a clear meaning before anything else. On this page, a feature is a small spot in a picture that can be found again. It also carries a list of numbers that describes what the picture looks like around it.

The idea in one sentence is that feature matching picks out corners in two pictures, describes the little patch round each corner as a list of numbers, pairs each corner with the corner whose list is most alike, and keeps only the pairs that agree on one single movement of the object.

For example, imagine that you have a photo of a cereal box, and that you want to find that box on a crowded shop shelf. You do not compare the whole photo with the whole shelf. Instead you pick out a few distinctive bits of the box, such as the corner of a letter or the tip of a leaf in the logo. Then you look for those same bits on the shelf, and you ignore the bits that look alike on several boxes. Once several of the bits you found sit in the same arrangement as on the photo, you have found the box. Feature matching does exactly this work, in the same order.

The next part of the page explains how it works, step by step. The example used all the way through is a flat printed label, such as the label on a box of parts. The program has a stored picture of that label, 200 by 140 pixels. Then the camera takes a picture of a cluttered table, 320 by 230 pixels. Because the camera looks at the table from an angle, the label appears in that second picture turned by about 11 degrees, a little smaller, and tilted. There is also a second, smaller sticker in the corner of the picture, and it carries part of the same print. That sticker is a trap, because its spots look exactly like spots on the label although it is not the label. The program's job is to find the label in spite of the sticker, and to say exactly where the label's four corners are in the camera picture. All the numbers given in this example come from a real test run.

Step one is to find spots that are easy to find again. The program cannot use every spot of that label, because not every spot in a picture can be found again. To see which spots can, think of a small square window placed on the picture. Then shift that window by a pixel or two, and ask how much the picture inside it changes. 

The page includes a diagram showing what happens when this window is shifted by up to 5 pixels in any direction. On a flat area, nothing changes whichever way the window moves, so the smallest change is zero and a spot there could be anywhere in the flat area. On an edge, the window changes when it moves across the edge but not when it slides along it, so the smallest change is again zero and a spot there could be anywhere along the edge. However, on a corner, every shift changes the window. The smallest change for any shift is greater than zero, meaning a corner can be found again to within a pixel.

That is why a program looks for corners, and the best-known test for them is the Harris corner detector. It measures, at every pixel, how much the brightness changes in the direction where it changes most, and in the direction where it changes least. Then it calls a pixel a corner when even the smaller of those two changes is large. The program also keeps only the pixel with the highest score in each small neighbourhood, so that one corner does not give ten spots.

In the example, this finds 46 corners in the stored label and 161 in the camera picture. The camera picture has more because it also shows the clutter round the label. The word keypoint is often used for a spot found this way. Instead of corners, some other detectors look for blobs, which are small round patches that are darker or brighter than their surroundings. The idea behind both is the same, because a good keypoint is one that moves with the object and nowhere else.

Step two is to describe each spot. Because step one gives nothing but positions, the program cannot yet tell one keypoint from another. To pair a keypoint with a keypoint in the other picture, it also needs to know what the picture looks like round that spot. So it turns the patch round each keypoint into a list of numbers, called a descriptor. Two patches that look alike then get lists that are alike, which is what makes pairing possible at all.

The example uses the idea inside ORB, which is the most common fast descriptor. It works in four steps. First, it smooths the picture a little, so that single noisy pixels matter less. Second, it finds the patch's own direction. The program takes the centre of brightness of the round patch and draws an arrow from the keypoint to it. If the object turns, this arrow turns with it. Third, it compares pairs of pixels. The program has a fixed list of 256 pairs of positions inside the circle, and it turns that whole list to the patch's own direction, so that for each pair it can ask if the first pixel is darker than the second. The answer is 1 for yes and 0 for no. Finally, the 256 answers, in order, form the descriptor, which is a string of 256 bits.

A diagram shows what this looks like for a corner in the stored label compared to the camera picture. In the camera picture, the label has been turned, so the patch's arrow points 15 degrees further round. The pixel pairs turn with the arrow, landing on the same parts of the pattern. As a result, the answers differ in only 9 of the 256 bits. A completely different corner in the camera picture is also shown, and its answers differ in 78 of the 256 bits.

The number of bits that differ between two descriptors is called the Hamming distance. Because a computer can count differing bits very fast, it is the distance that this kind of descriptor uses.

The page lists three well-known descriptors. First is ORB, from 2011. It stores 256 bits, uses the Hamming distance, is fast, and handles turning and size changes. Second is SIFT, from 1999. It stores 128 numbers and uses ordinary straight-line distance. It counts the directions of brightness change in a grid of small squares round the keypoint. It is slower, but handles size change, turning, and light changes very well. Finally, AKAZE, from 2013, stores a few hundred bits and uses the Hamming distance. It finds keypoints in a way that keeps object edges sharp, and sits between ORB and SIFT in speed and quality.

Step three is to match the descriptions. Once every keypoint carries a descriptor, the program can pair the keypoints up. For each keypoint in the label, it finds the keypoint in the camera picture whose descriptor is closest. This is a nearest-neighbour search, but in the space of descriptors rather than in the space of positions. In the example, 38 of the 46 label keypoints get a right partner, meaning the partner lies within 3 pixels of where the label corner really is. The other 8 pairs are wrong.

Step four is the ratio test. Some wrong pairs can be spotted even without knowing which ones are wrong. If a keypoint's best partner is only a little better than its second-best partner, the program cannot really tell the two apart. This happens on repeated patterns. The ratio test uses exactly that difference. It keeps a pair only when the distance to the best partner is less than zero point eight times the distance to the second-best partner. 

A diagram plots each label keypoint based on these two distances, with a dashed line showing the ratio test limit. The dots below the line pass the test. A table shows the results for the 46 pairs. The ratio test threw away half of the wrong pairs and lost only 2 right ones. But 4 wrong pairs passed it easily. Because all four of them point at the trap sticker, which carries the same print, these pairs look perfect on their own. No test that looks at one pair at a time can catch them.

Step five is to clean up with RANSAC. Since no test on a single pair can catch those last four, the final step uses a fact about the pairs as a group. The right pairs agree with each other, while the wrong ones do not. When a flat object is seen by a camera, every point on it moves from the stored picture to the camera picture by one and the same rule, which is called a homography. A homography is a 3 by 3 table of numbers that maps the points of one flat surface to the points of another. It can be computed from four pairs of points.

Because the wrong pairs do not agree with the homography of the right pairs, the program uses RANSAC. The method repeats four steps many times over. First, pick four pairs at random. Second, compute the homography that fits those four exactly. Third, move every label keypoint by that homography, and count how many of them land within 3 pixels of their partner, because those pairs are the inliers. Finally, remember the homography with the most inliers.

A diagram shows the final result. Of the 40 pairs left after the ratio test, 36 agree with one homography. The 4 wrong pairs pointing at the second sticker are thrown away. A blue outline shows the label's edge moved by the final homography, and each of its four corners is within 0.75 pixels of where the label corner really is. RANSAC found this on its 18th try. For four pairs at a time and nine in ten right, 5 tries already give a 99 percent chance of one clean try, so real programs stop early once they find a good answer.

The page provides pseudocode for all five steps. It defines a process that detects and describes keypoints in both pictures, pairs them up, and applies the ratio test. If there are enough pairs, it runs the RANSAC loop to find the homography with the most inliers. The minimum number of inliers matters greatly. Because RANSAC always returns its best try, it returns one even when the object is not in the picture at all. A rule such as requiring at least 10 inliers turns that best try into a clear "not found".

The next section explains where this is used on a robot arm. Feature matching is used wherever the arm has to find an object that has printing or texture on it, from a camera picture alone. First, it is used for finding a textured part or package, even when it is turned or partly hidden. Second, it finds the pose of a flat object from a homography, which can be turned into a 3D position using the camera's lens numbers. Third, it feeds pose from points. When the object is not flat, the program stores a 3D model whose surface points carry descriptors, and pairs those with the camera picture to compute a 3D pose. Fourth, it provides a first guess for Iterative Closest Point on a depth scan. Fifth, it follows the camera's own movement by matching keypoints from one picture to the next, which is the core of visual odometry. Finally, it keeps track of objects that sit close together when position alone cannot tell them apart.

However, feature matching is not always useful. It assumes the object gives the program something to match. The page lists common problems and what to use instead. If the object has no texture, like plain grey plastic, you will get too few keypoints, so you should use a depth scan or the object's outline instead. On a shiny surface, keypoints land on reflections that move when the camera moves, requiring different lighting or a depth camera. On a repeated pattern, the ratio test throws away most pairs, so you must match on parts that do not repeat or add a printed marker. If there are two copies of the same object, RANSAC might lock onto one and switch between them, so you must find one, remove its inliers, and run RANSAC again. For a large change in viewing angle, few pairs pass the ratio test, so you should store pictures from several angles. If there is motion blur, corners smear out, so you must take the picture when the arm is still. Finally, if the object is not flat but a homography is fitted, RANSAC finds only the inliers on one face, so you should fit a pose from a 3D model instead. When nothing on the object can be relied on, people often stick a printed marker on it, such as an ArUco or AprilTag marker.

None of these steps has to be written from scratch. The page lists well-known libraries that provide them. OpenCV is the usual choice for C++ and Python. It provides ORB, SIFT, AKAZE, matchers, and RANSAC homography functions. SIFT has been in the main package since its patent ran out in 2020. Scikit-image in Python is easy to read but slower. Kornia and LightGlue provide learned matchers that run on a graphics processor. For a first try on a robot arm, OpenCV's ORB with a brute-force Hamming matcher, the ratio test, and its homography function is a few lines of code and runs on an ordinary processor.

The page then asks why we use feature matching and what it costs. It tells you where a known textured object is, needing no training data because one picture is enough. The obvious alternative is template matching, which slides the whole stored picture over the camera picture. Template matching is simple and works well when the object is always the same way up and the same size. But it fails as soon as the object is turned, tilted, nearer, further away, or partly covered. Feature matching handles all of these. These advantages come with costs. The object must have texture, wrong pairs are normal so RANSAC is always needed, thresholds need tuning for each camera, and the result is only a pose in the picture, meaning you still need camera calibration to get a pose in the arm's frame.

There is also a learned alternative. Since about 2018, neural networks have been trained to do these steps. SuperPoint finds and describes keypoints in a single network. SuperGlue and LightGlue pair them by looking at all of them together. LoFTR skips keypoints and matches the two pictures directly. They find many more right pairs on hard pictures, such as large changes of angle or poor light. Even so, RANSAC is still used after them. They need a graphics processor to run at camera rate and a large set of model weights. A classical matcher is still the better first choice when the object has good texture and the camera angle does not change much.

It creates an ORB detector and computes keypoints and descriptors for both pictures. It then uses a brute-force matcher with the Hamming distance to find the two best partners for each spot. Finally, it uses the find homography function with RANSAC and a 3-pixel threshold to find the movement that most pairs agree on. 

The library does all five steps for you, but you still write the ratio test yourself, which is why every tutorial contains the same line of code for it. You also decide what counts as having found the object. The usual test is to count the inliers and require at least ten or fifteen, and then check that the four corners of the stored picture still make a sensible shape. You have to decide three numbers: the maximum number of features, the ratio test threshold, and the RANSAC pixel limit. Lowering the ratio test throws away more pairs but leaves cleaner ones, which is what you want on a repeated pattern. Finally, remember that none of these numbers helps on an object with no texture, and no amount of tuning will find a plain white box this way.
