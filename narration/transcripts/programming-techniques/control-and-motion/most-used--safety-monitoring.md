Safety monitoring. This page explains the software layer that watches every command on its way to the arm and stops or limits the ones that are unsafe. It answers five questions. What does the layer check, and how does each check work with real numbers? How do you check the commands of a learned policy, which can output anything, and what happens when the commands stop arriving? And what is this layer not, meaning where does it stop and where must certified safety equipment take over?

It is written for a reader who already knows about PID control, trajectory generation, joint limits, and speed limits. It also helps to understand sensor streams, because a safety check is a threshold on a stream. Every number mentioned comes from a real run of the page's diagram script.

Before we begin, a warning. Nothing on this page is a certified safety function, meaning one that has been designed, tested and approved to a safety standard and that runs on hardware built for it. The software layer described here runs on an ordinary computer, in ordinary code, so it catches mistakes and makes the arm better behaved. But it must never be the only thing between the arm and a person, and a later section draws that line in full.

The first section explains what this page answers. An arm does whatever its commands say, and those commands come from a planner, a teleoperation joystick, a visual servo loop or a learned policy. But any of them can be wrong. For example, a planner can be given a bad goal, a network cable can drop, and a learned policy can output a target a metre away for no reason anyone can see.

Because of that, a safety monitor is a small piece of code placed between the command sources and the arm's controller. It checks every command against a list of rules, and if a command breaks a rule, the monitor limits it, refuses it, or stops the arm. It also watches the arm's sensors, so it can stop the arm when something is happening that no command asked for.

Those rules fall into six groups. First, joint position, speed and torque limits. Second, checks on a learned policy's output. Third, a workspace box, and keep-out zones inside it. Fourth, a watchdog that stops the arm when commands stop arriving. Fifth, speed and separation monitoring, which means slowing down as a person comes closer. And finally, power and force limiting, to keep contact gentle.

The next part gives the idea in one sentence. Since those six groups of rules all do the same kind of job, here is that job. Check every command against simple, fixed rules just before it reaches the arm, and when a rule is broken, prefer stopping and saying so over quietly changing the command.

Here is an everyday example of the same idea: a driving instructor's car with a second brake pedal on the passenger side. The learner does the driving, while the instructor does not steer and does not try to drive better than the learner. Instead, the instructor watches for a few simple things: too fast, too close, the wrong side of the road. When one of them happens, the instructor brakes. But that second pedal is not a replacement for seat belts and airbags, which work even if both people make a mistake. So a safety monitor is the instructor's pedal, while certified safety functions are the seat belts.

The next section explains how it works, step by step, starting with where the layer sits. Because the monitor has to see every command, it sits after every command source and before the controller. Two facts matter here. First, the standard trajectory controller checks less than people assume. Its tolerances default to zero, and zero means "do not check". So by default nothing compares where a joint is with where it should be during a move. A monitor that checks the following error, which is the gap between the commanded and the measured position, fills that gap. Second, speed scaling is a request, not an enforcement. A software speed limit is also a request, only a more careful one. Enforcement belongs to the certified functions in the robot's own controller.

The monitor runs at the control rate, often a hundred to a thousand times a second. So each check must take a tiny, fixed amount of time, which is why the checks are kept simple: comparisons, clamps and a few multiplications.

The simplest rules are the ones about a single joint. Every joint has a range it can move through, a top speed, and a largest torque, where a torque is a turning force measured in newton metres. The arm maker gives the hardware limits, so a monitor uses software limits set a little inside them, and the software then stops the joint before the hardware has to.

There are two ways to apply such a limit. Clamping replaces a value outside the range with the nearest value inside it, while refusing rejects the command, keeps the arm where it is, and reports a fault. So clamping keeps the arm moving, whereas refusing tells you that something is wrong.

A speed limit is applied by rate limiting, which means the target may move at most the speed limit multiplied by the time step from one tick to the next. At 2.5 radians per second and 100 ticks a second, that comes to 0.025 radians per tick.

The joint limits apply to any command source, but one source needs more care than the rest. A learned policy is a neural network that turns camera pictures and joint angles into commands. Unlike a planner, a policy has no built-in idea of the arm's limits or of obstacles. So its output must be checked every single time.

The page shows a diagram of one elbow joint driven by such a policy. The policy sends a new target 10 times a second, while the monitor runs 100 times a second. The diagram shows joint targets from a policy going above a 1.6 radian limit, and including one bad output of plus 0.9 radians.

Two things go wrong in the policy's output. Around one second, it asks for up to 1.70 radians, past the 1.6 radian software limit. The monitored versions clamp this, and the joint stops at 1.60 radians. Then, at two seconds, one output jumps 0.9 radians above its neighbours for a tenth of a second. The biggest step in the raw targets is 1.10 radians in one tick.

If the monitor only clamps and rate limits, it never moves faster than 2.5 radians per second and its biggest step is 0.025 radians per tick. But it still moves towards the bad target, and the joint goes 0.25 radians, or about 14 degrees, the wrong way before the next good output arrives. In other words, rate limiting has turned a jump into a smooth, believable mistake.

However, if we add one more rule that compares each new output with the last good one, we can refuse a step of more than 0.3 radians per output. The joint then holds the last good target and a fault is logged. As a result, it logs exactly one fault at two seconds, and the joint never moves towards the bad target.

This is why a monitor for a learned policy checks more than the limits. The usual checks are these. First, the output is a real number, meaning no infinity and not a "not a number" value. Second, the output is fresh, meaning its time stamp is recent and it was computed from a recent picture. Third, each joint target is inside its limits. Fourth, the step from the last accepted output is small enough. Fifth, the tool position it implies is inside the workspace box and outside every keep-out zone, which is computed from the joint targets using forward kinematics. And finally, the expected force is within limits, and the measured force is too.

The checks so far were all on joint angles, but some rules are easier to state in the space the tool moves through. A workspace box is a region the tool must stay inside, while a keep-out zone is a region inside that box which the tool must never enter, such as a camera stand, a fixture, or the part of the table where a person works. Both are usually boxes, because the check is then only a few comparisons.

But the tool is not a point, so each check treats the gripper as a sphere around the tool point, 40 millimetres in radius here. That is the same as moving the box's walls in by 40 millimetres and the keep-out zone's walls out by 40 millimetres.

A diagram shows a top view of a table with a green allowed box, a red keep-out zone for a camera stand, and a tool path. The box runs from 150 to 700 millimetres away from the base and from minus 450 to 450 millimetres across. The camera stand's keep-out zone runs from 380 to 560 millimetres and from 180 to 320 millimetres. A command asks the tool to go in a straight line from 300, minus 200, to 600, 380, making the whole path 653 millimetres long. The goal itself is inside the box, so a check on the goal alone would pass it.

Instead, the monitor checks points every 5 millimetres along the path. At 380 millimetres along, the gripper's sphere would come within 40 millimetres of the keep-out zone, so the monitor stops the tool there, just before the gripper would touch it. A second goal is outside the box altogether, so it is refused before the arm moves at all.

A path planner with a collision model also avoids the camera stand, but the monitor is still useful because it checks the commands that did not come from the planner, like a joystick, a servo loop, or a policy.

The checks above all assume that commands keep arriving, but many command sources send a stream, such as "move at this speed" 100 times a second. If the sender freezes or the network drops, the last command may stay in force, and the arm keeps going at the last speed.

Because of that, a watchdog is used. This is a timer that every new command resets. If the timer runs past a timeout with no new command, the watchdog stops the arm. The name comes from a dog that barks when it stops hearing its owner.

A diagram shows speed commands arriving 100 times a second until one second, then stopping. Without a watchdog, the tool keeps moving at 200 millimetres per second, and it would keep going until something else stopped it. But with a 0.1 second timeout and braking at 2 metres per second squared, the tool stops at 1.19 seconds, 28 millimetres after the last command arrived.

The timeout itself is a trade. A short one stops the arm sooner, but it also stops it whenever the computer is briefly busy, so a common choice is a few times the normal gap between commands. The braking distance after the timeout must also fit inside the free space around the arm. A watchdog can also run in both directions. If the state messages stop, the monitor cannot see the arm, and it should stop sending motion.

The rules so far protected the arm and the work, but two of the six groups are about people. Speed and separation monitoring slows the arm as a person comes closer, and stops it when the person is too close. It needs a sensor that measures where people are, such as a laser scanner on the floor or a camera above the cell.

The rule itself comes from one question: if the person walked straight at the arm now, could the arm stop before they met? The gap needed is the sum of four distances. First, how far the person walks while the system notices and while the arm brakes. Second, how far the arm moves before it starts braking. Third, how far the arm moves while braking. And fourth, a margin for sensor error and the size of a hand or arm.

A diagram illustrates this with example numbers. The person walks at 1.6 metres per second, while the sensor and software take 0.1 seconds to react. The arm brakes at 2 metres per second squared, the margin is 0.1 metres, and the arm's top speed is 0.5 metres per second.

At full speed the arm needs a gap of 0.77 metres, and at a standstill it still needs 0.26 metres, because the person keeps walking while the system reacts. In between, the monitor chooses the highest speed whose gap fits, so at 0.6 metres that is about 0.34 metres per second. As a person walks up from 2.6 metres, the arm starts slowing and is stopped when the person is 0.25 metres away. Then when they walk away, it speeds up again.

A software version of this is useful for keeping a cell running smoothly. But the version that protects people must use a safety-rated sensor and a safety-rated controller, with the distances and speeds worked out by the method in the standards.

Instead of keeping people away, power and force limiting is the other way to work near them. The arm is allowed to touch a person, but only gently, so that the force and the pressure of any contact stay below set values. Collaborative arms, often called cobots, are built for exactly this.

Two things decide how hard a contact is. The first is the force the controller is pushing with. The second is the energy of the moving arm when it meets something, and that kinetic energy grows with the square of the speed. A moving mass of 2 kilograms at 0.25 metres per second carries 0.0625 joules, while at 1 metre per second it carries 1 joule, sixteen times as much. This is why power and force limiting always comes with a speed limit as well.

A software force monitor watches the wrist force, or the gap between the expected and the measured joint torques. It uses a filtered signal, a threshold with hysteresis, and a short debounce. The debounce must be short, because every millisecond of waiting lets the force grow further.

The section ends by summarizing these steps as pseudocode. Every control tick, the monitor checks the watchdog timers. Then it checks the command itself, refusing it if it is not a number or if the jump from the last good command is too large. It clamps the position to the soft limits, and clamps the step size to the speed limit. Next, it computes the tool position using forward kinematics, refusing the command if the tool is outside the workspace box or inside a keep-out zone. Finally, it checks the sensors, stopping if the following error is too large or the force flag is on, and scales the step so the tool speed stays within the allowed speed for the distance to the nearest person.

The next section covers where this is used on a robot arm. Because every command source can be wrong, a software safety layer is used almost everywhere an arm moves under program control. This includes running a learned policy, where every output is checked before it reaches the arm. It is used in teleoperation, where a watchdog stops the arm if the link drops, and a workspace box stops the person steering it into the table. It is used in visual servoing to catch a stopped camera or a wrong detection. It is used in contact tasks, where a force limit stops the task when it trips. It is used in development and testing, letting people try new code without risking the arm. It is used in shared cells, slowing the arm early so the certified function rarely has to stop it hard. And it is used to check the controller's work, catching an arm that has hit something or a joint that is slipping.

The next part explains where it is useful, and where it is not. The software layer is the right tool for catching mistakes in commands, keeping a cell running smoothly, and protecting the arm and the work. But it is not the right tool for protecting people on its own.

The page provides a table of what can go wrong and what to use instead. For example, clamping can hide a bad command, making the arm move smoothly but the wrong way; instead, you should refuse jumps and log them. Limits set too tight cause frequent stops, leading people to disable them; instead, measure normal peaks and set limits with a margin above them. If the monitor runs on the same computer as the fault, a crash takes the monitor down too; this requires a watchdog in the arm's own controller. If only the goal is checked, the tool might pass through a keep-out zone; you must check points along the path. If a force threshold uses a heavily filtered signal, stops come late; use a short filter for the stop. If the person sensor misses someone, the arm does not slow; this needs safety-rated sensors. Finally, if the monitor is trusted as a safety function, someone could be hurt; you must use a risk assessment and certified safety functions.

The next section lists libraries that provide these checks. Most of these checks already exist in the usual tools. In C++, the ros2_control joint_limits package reads limits from the robot description. The ros2_controllers joint_trajectory_controller has tolerances on following error and a timeout for stale commands. MoveIt 2 provides real-time steering with collision checking and joint limits, and uses collision objects for keep-out zones. The libfranka library provides rate limiting and contact detection thresholds. Most importantly, the arm maker's safety settings, set on the teach pendant, run in the robot's own controller. Some of these are safety-rated. You should set those first, and let the software layer add only the checks that your program alone can know about.

The next section emphasizes that this is not a certified safety function. A software limit is a request, and a safety-rated function is an enforcement. A certified safety function has four things the software does not. It runs on hardware built for safety, often with two channels that check each other. Its design, failure rates and tests are documented against a safety standard. It keeps working when the ordinary software crashes or freezes. And its stopping times and distances have been measured on the real arm.

Two standards cover this for robot arms: ISO 10218 for industrial robots, and ISO/TS 15066 for collaborative robots. They describe safety-rated monitored stops, hand guiding, speed and separation monitoring, and power and force limiting. Outside of software entirely, an emergency stop is a large red button wired to cut the motors' power directly, and a risk assessment is a written study of how the cell could hurt someone. The certified functions and the emergency stop are what protect people, while the software monitor protects the arm and the work, catching mistakes early so the certified limits rarely have to trip.

The next part asks why we need a software safety layer, and what it costs. It gives the arm limits that know about the task, a stop when commands stop arriving, and a clear record of why it stopped. Relying on the arm's built-in safety functions alone means they do not know that a camera stand is on the table, or that a policy's output jumped, and they usually stop the arm hard, which ends the task. Trusting a planner is also not enough, because it only checks the path it makes, not a joystick or a policy.

The costs are that every limit must be measured and maintained. Limits set too tight cause false stops. The checks add a little delay, and the monitor can fail together with the computer it runs on. But the largest cost is a false sense of safety, because a monitor that works well in testing can make people treat it as a certified function, which it is not.

The next section discusses the learned alternative. Because the value of this layer is that every rule is plain and does the same thing every time, there is no learned model that replaces it. Learned models can add to one part of the layer, the contact checks, by learning the normal gap between expected and measured torque to notice a dropped object or gentle bumps. But like this layer, they sit on top of the certified safety function, never instead of it.

The final section shows how to use it in Python. While the tools mentioned earlier are configured in C++, this section shows the Python you would actually write. The code defines constants for minimum and maximum joint angles, maximum velocity, an allowed workspace box in metres, and a command timeout of 0.1 seconds.

It creates a SafetyMonitor class that checks each command. If no command arrives within the timeout, it returns a message saying so. If the tool's position is outside the allowed box, it returns a message that the tool is outside the box. It then applies a speed limit by clamping the step size, and a position limit by clamping the final joint angles. Returning "None" means "do not move", and the caller then holds the arm where it is or starts a stop. The only library call is numpy dot clip, which clamps an array between two bounds.

When you work in ROS 2, the sensible division is to let the C++ tools hold the limits that come from the arm's description, and to write in Python only the checks that your own program knows about, such as a keep-out box that exists because of where you put the conveyor. You have to decide or measure every number in that file. The joint and speed limits come from the arm's manual. The workspace box comes from measuring your cell in the arm's base frame. The timeout has to be a small multiple of your command period. And a speed limit meant to protect a person has to come from a risk assessment and from the numbers in the safety standards, not from what looked smooth on the day.
