Point cloud models. This page is about neural networks that read a point cloud directly, so it answers three questions. How can a model take in a list of 3D points that has no order, what does it give back to a robot arm, and when is it better than turning the points into a picture and using an ordinary image model? 

It assumes you already know what a point cloud is, and that a neural network is made of layers that turn a list of numbers into another list of numbers. It also helps to know about clustering, which splits a point cloud into objects using written rules and thins it onto small cubes called voxels, because this page shows what a trained model adds.

The first section explains what a point cloud model is. It is a neural network that takes a list of 3D points and says what they are. For example, imagine someone gives you a sheet of paper with a thousand rows. Each row has three numbers, which are the x, y, and z coordinates of one spot on some object. The rows are in a random order, and your job is to say whether the object is a mug, a bottle, or a book. A person would plot the dots first and then look at the shape, but a point cloud model has to do the same job without plotting anything, because it only has the numbers.

The next part covers what goes in and what comes out. The sheet of paper with rows of numbers is close to what the model really gets. A point cloud model takes in one point cloud, and each point in it has at least three numbers, which are x, y, and z. Some models also take the colour of each point, as three more numbers for red, green, and blue. Before the cloud goes in, the software usually cuts it down to a fixed number of points, such as 1,024 or a few thousand. It does this by picking points spread evenly over the cloud, because a full depth camera shot has far more points than a model needs.

What comes out depends on the job, and there are two common jobs. First is classification, which gives one name for the whole cloud, such as "mug", together with a number between zero and one that says how sure the model is. Second is segmentation, which gives a name to every single point. On a table scene, each point is marked "mug", "box", or "table". On a single object, each point can be marked with a part name instead, such as "handle" or "body", and that is called part segmentation. 

An illustration of segmentation on a small table scene shows the model seeing only positions on the left, so every dot looks the same. On the right, every dot has a name, which is shown by giving each object its own colour. For a robot arm, segmentation is usually the more useful of the two jobs. Once the arm knows which points are the mug, it can work out where the mug is, how big it is, and where to put its fingers.

Moving on to how it works inside, the random order of those rows is the first thing the design has to deal with. An image model can rely on order, because pixel number five in a row is always next to pixel number four and pixel number six. A point cloud has no such order, since the camera driver can list the points in any order it likes and it is still the same scene. To picture this, imagine the same five points arranged in two different lists. The order is different, but a point cloud model must give the same answer for both. An ordinary network cannot do that, because it treats the first number in its input list differently from the second. If you fed it the first list and then the second, it would see two different inputs and could give two different answers. That means a point cloud model needs a design that ignores order altogether.

The first model that solved this well is called PointNet, published by researchers at Stanford University in 2017. It works in four steps. First, it takes one point, as its three numbers. Second, it passes it through a small network, which turns those three numbers into a longer list of numbers. In the real PointNet this list has 1,024 numbers. Third, it does the same for every other point, using the exact same small network, so that every point now has its own list of numbers. Finally, it looks along each position in those lists and keeps only the largest number, an operation called max pooling. The result is one list for the whole cloud. A last small network then turns that one list into the answer, such as "mug". 

In this process, every point goes through the same network to create a column of numbers. The largest numbers in each column are kept, and these become the list for the whole cloud. This fourth step is what removes order, because the largest number in a column is the same whichever row it sits in. If you shuffle the points, the rows move but the largest numbers stay the same. 

Each number in the lists comes to stand for some small feature of shape. One number might come out large for points on a curved surface, while another might come out large for points far from the middle. Nobody chooses these features, because the network learns them during training. The largest value in a column then says that somewhere in this cloud there is a point with this feature. For segmentation, PointNet goes one step further and sticks the list for the whole cloud onto each point's own list. Each point then knows about itself and about the whole shape, so a last small network can give each point its name.

However, PointNet has one weakness, which is that each point goes through the small network alone and never looks at the points right next to it. So it is poor at small details, such as the thin gap between a handle and the side of a mug. PointNet++, from the same group later in 2017, fixes this by looking at small groups of nearby points first. At first, each centre point looks only at the dots inside a small circle around it. Then, those groups are grouped again to cover a larger area. It works in rounds, and in each round it does three things. First, it picks a number of centre points, spread out over the cloud. Second, for each centre, it collects the points within a small distance of it. Third, it runs a small PointNet on just that group, which gives one list of numbers for the whole group. The next round then uses the centres of those groups as its points, with a bigger distance. So the model first learns the shape of small patches, then of larger parts, and then of the whole object. This is the same pattern that image models use when they look at small patches of pixels first, which is described on the page about image classification.

Besides PointNet and its neighbour groups, two other designs are common today. The first cuts space into small cubes called voxels, where a voxel is simply a 3D pixel. The model marks each cube that has a point in it and then works on the grid of cubes. Most cubes in a room are empty air, so the model only computes on the cubes that hold points. That trick is called sparse convolution, and it is fast on large scenes. The second design uses attention, which is a way for each point to look at other points and decide which of them matter to it most. It is the same idea that language models use to decide which words in a sentence matter to each other. Point Transformer models use it on groups of nearby points.

The next section explains how it is trained. Whichever of those designs a model uses, it learns from point clouds that people have already labelled. For classification, each example is a whole cloud with one name, while for segmentation each example is a cloud with a name on every point. Most of that data comes from one of three places. First, collections of 3D shapes made on a computer, such as ModelNet40 and ShapeNet. ModelNet40 has about 12,000 shapes in 40 kinds such as chairs, cups, and aeroplanes. Software then samples points from the surface of each shape to make a cloud. Second, scans of real rooms, such as ScanNet, which has more than a thousand scans of indoor rooms made with a depth camera, where people marked each part of each scan by hand. Third, simulation, where a robot team places 3D models of its own objects in a simulated bin and makes a simulated depth camera look at them. The simulator knows which object every point came from, so the labels cost nothing.

Training itself works by having the model guess the names first. Then the training program compares them with the right names and adjusts the network a little so that the next guess is closer. This whole loop repeats many thousands of times before the model is any good. One more step in training makes a large difference to the result. The program turns each cloud by a random angle, moves it a little, and shakes each point by a small random amount. This teaches the model that a mug turned sideways is still a mug, and it also prepares the model for the noise a real depth camera adds.

The page then lists well-known models that appear in robot papers and code. PointNet from 2017 was the first widely used network that reads points directly, using one shared small network and max pooling. PointNet++, also from 2017, adds groups of neighbouring points at several sizes, and is still a common part inside robot grasp models. DGCNN, short for dynamic graph convolutional neural network, from 2019, links each point to its nearest neighbours and learns from the differences between them, finding new neighbours at each layer based on what that layer has learned. MinkowskiEngine, from 2019, is a library for sparse convolution on voxels, used for many models of large indoor scenes. Finally, Point Transformer from 2021 and Point Transformer V3 from 2024 use attention on groups of nearby points, making them among the strongest models on scans of rooms.

To make this concrete, the next section gives a worked example of picking a mug from a cluttered table. An arm has a depth camera on its wrist, and a mug, a box, and a few other things stand on a table. The job is to pick up the mug, and it happens in six steps. First, the arm moves its camera above the table and takes one depth shot, and the software turns that shot into a point cloud of about 300,000 points. Second, the software cuts the cloud down to the region over the table and picks about 20,000 points spread evenly over it. Third, a segmentation model gives every point a name, and about 1,500 points come back as "mug". Fourth, the software takes only the mug points. Their average position is roughly the middle of the mug, while the highest mug point gives the height of the rim. Fifth, a part segmentation model, or a second pass of the same model, marks which mug points are the handle, so the arm now knows which way the handle points. Finally, the mug points go to a grasp model, which picks a place for the fingers. The numbers in this example are only there to make the steps concrete, because the real counts depend on the camera and on how far away it is.

The following section covers what goes wrong when the points are not there to be named. There are four main problems. First is missing points. A depth camera often gets no reading on shiny, dark, or see-through surfaces, so a glass has almost no points. People fix this by predicting depth for those pixels with an image model, or by building the scene from many photos. Second, the back is missing. The camera only sees one side, so the mug points are a half shell rather than a whole mug. That means the average of those points is nearer the camera than the real middle of the mug. Third, a different sensor. A model trained on clean computer shapes can do badly on real, noisy clouds, and a model trained on one depth camera can do badly on another because of different noise. The usual fix is to train with added noise and then to fine-tune on a few hundred labelled clouds from the real camera, which means training an already trained model a little more on new data. Fourth, objects it has never seen. A model trained on 40 kinds of object only knows those 40 names, so a new kind of object gets one of the old names. One way around this is borrowing names from an image model that has learned many thousands of words.

The next part asks why you would choose this rather than an image model, and what it costs. A point cloud model gives a robot arm the object's points directly in 3D, in the same metres the arm moves in. The obvious alternative is to leave the depth camera's output as a picture, feed that grid of distances and the colour photo to an ordinary image segmentation model, and turn the chosen pixels into points afterwards. There are three reasons to choose a point cloud model instead, all coming from working in metres rather than pixels. First, a point cloud does not depend on where the camera is in the same way. A mug seen from close up covers many pixels, but from far away it covers only a few. In a point cloud, it is the same size in metres in both cases. Second, you can merge several point clouds into one, since two cameras give two clouds that fit together in the same room. Two pictures taken from different places cannot simply be added together like that. Third, many grasp models expect points, so giving them points from a point cloud model saves one conversion step. 

However, what it costs you comes in three parts. First, and biggest, there is far less labelled 3D data than labelled photo data. Image models learn from hundreds of millions of photos, so they often know many more kinds of objects. Second, it depends completely on the depth camera, so where the camera fails, the model has nothing to work with. Third, it needs a graphics card for large clouds, and a step that cuts the cloud down first. In practice, many robot systems do both. They run an image model on the colour photo to find and name the object, and then they use the depth points inside its outline. A point cloud model is the better choice when shape matters more than colour or printed labels, for example when parts in a bin all look alike.

The page then mentions the written alternative. You can find objects in a point cloud with a written recipe instead. A method called RANSAC finds the table plane so that it can be removed, and then clustering groups the points that are left into one cluster per object. The recipe needs no labelled clouds, and it works on objects the robot has never seen. However, the point cloud model wins when objects touch, as they do in a full bin, because clustering merges touching objects and nothing in it can fix that. It also wins when the robot must name the parts of an object, such as a handle.

The final section is about using it in Python. It explains how to prepare the data, using the Open3D library to load a point cloud from a file and thin it down using small voxels. Then, it converts the points into a batch format the model expects, and uses the PyTorch3D library to pick exactly 1,024 points spread evenly over the cloud, rather than just taking the first points in the file. What is packaged for you out of the box is exactly this preparation. Open3D and PyTorch3D are proper installable libraries. However, the networks themselves, like PointNet++ or Point Transformer, are released as research repositories. There is no simple install command or import you can write, and there are no widely shared trained weights for the objects on your table. If you want to build one of these networks, PyTorch Geometric supplies the layer, and you assemble and train the network around it yourself. 

In reality, most robot projects never call a point cloud network directly. Instead, they use one inside something else. A grasp model takes your point cloud and gives back grasps, with a PointNet++ hidden inside it that you never touch. That is the realistic route, and the preparation code described is still the code you write, because a grasp model expects the cloud prepared in just this way. What you have to decide is the number of points and the voxel size, and they trade against each other. A model trained on 1,024 points will not read 20,000, and the points you throw away are gone, so a thin mug handle can disappear before the network ever sees it. You also decide whether you need a point cloud model at all, because a detector on the colour picture plus the depth at those pixels is easier to get working and is often enough.
