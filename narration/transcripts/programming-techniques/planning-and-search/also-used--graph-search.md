Graph search. This page explains graph search, which means finding the shortest or cheapest route through a set of places that are joined by moves. It covers the three methods everyone uses: breadth-first search, Dijkstra's algorithm, and A star. The page answers four questions. How does each method work, and when is each one the right choice? Where does a robot arm use them, and when should you use something else instead? The eighth section then adds one more graph method that answers a different question: in what order must things be done, when some must come before others?

It is written for a reader who has read the chapter overview, and you do not need to have taken an algorithms course. This is because every term is explained where it first appears. Every number on this page also comes from a real run of the code.

Graph search also matters well beyond this page and beyond robot arms. For example, the probabilistic roadmap on the next page uses it to answer every query, and a satellite navigation app uses it every time it finds a route.

The first section gives the idea in one sentence. Graph search grows outwards from the start, one place at a time, always taking next the place that is cheapest to reach so far, until it reaches the goal.

An everyday example shows how this works in ordinary life. You are in a large building and want to reach a meeting room, but you do not know the way. So you try every corridor one door at a time from where you stand. Each time you reach a door, you write on a sticky note which door you came through. When you finally reach the meeting room, you follow the notes backwards, and that gives you the route. Breadth-first search works in exactly this way, one door at a time. The other two methods then add one rule each. Dijkstra's algorithm counts how long each corridor is, and A star also looks at a sign that says roughly which way the meeting room is.

The next part of the page explains the words used for graphs and grids. The example above talks about places and moves, so this section gives those things their proper names. A graph is a set of places joined by moves, where the places are called nodes and a move between two nodes is called an edge. Each edge can have a cost, which is a number that says how bad it is to take that move. For example, the cost can be a distance, a time, or anything else you want the route to keep low.

Two kinds of graph come up on a robot arm, and the rest of this page uses both of them. First, a grid cuts a space into equal squares, called cells, and each free cell is a node joined by an edge to its neighbours. On this page a cell has four neighbours: up, down, left, and right. A cell that holds an object is left out, so no route can pass through it. Second, a roadmap is a small graph where each node is a pose the arm can be in, and each edge is a move between two poses that is known to be safe. A person can make a roadmap by teaching poses, or a program can make one by sampling, as the next page shows.

A route, also called a path, is a list of nodes where each one is joined to the next by an edge. Its cost is the sum of the costs of its edges. The search wants the path with the lowest cost of all the paths that reach the goal.

The third section explains how it works. Now that the words are settled, here is how the three methods actually run, and all three of them share one loop. They keep a list of nodes that they have reached but not yet looked at, and this list is called the open list. On each turn of the loop, they take one node off the list, look at its neighbours, and add the new ones. So the three methods differ only in which node they take off next.

The examples in this section all use one grid, which is a table seen from above, cut into five-centimetre squares, sixteen across and ten deep. The gripper moves at a fixed height. So a square counts as occupied when something on the table is taller than that height, such as a box, a tray of parts, a bottle, and a jar. Of the one hundred and sixty squares, thirty-five are occupied and one hundred and twenty-five are free. In every example the gripper starts at a start node and must reach a goal node.

The first method is breadth-first search, which finds the fewest steps. It takes nodes off the open list in the order they were added, so the first node added is the first taken off. A list that works this way is called a queue, like the queue at a shop counter.

This makes the search spread out in rings. It first reaches every cell one step from the start, then every cell two steps away, then three, and so on. So the first time it reaches a cell, it has already found the fewest steps to that cell.

The steps to do this are as follows. First, put the start on the queue and write zero steps next to it. Second, take the first cell off the queue. Third, for each free neighbour that has no number yet, write the cell's number plus one, remember which cell you came from, and add the neighbour to the back of the queue. Fourth, repeat from the second step until the goal comes off the queue. Finally, follow the notes backwards from the goal to the start to get the path.

The first diagram shows the real result of running that loop on the grid. The number in each cell is its distance from the start in steps, and the colour gets darker as the number grows, so you can see the rings spread around the box. The pale blue line is the path, which is twenty steps long, and every number along it is one more than the one before. The white cells at the right were never reached, because the search stopped as soon as the goal came off the queue. By then it had taken ninety-eight cells off the queue and reached one hundred and six in all.

Breadth-first search finds the fewest steps, but it does not know that some steps may cost more than others. When every step costs the same that is all you need, and the next method is what you reach for when it is not.

The second method is Dijkstra's algorithm, which finds the lowest total cost. Named after Edsger Dijkstra, who published it in 1959, it handles edges with different costs. It does this by always taking off the open list the node with the lowest total cost found so far. A list that always gives back its smallest item is called a priority queue.

When a node comes off the list its cost is final, and no later route to it can be cheaper. This is because every other node on the list already costs at least as much, and costs can only grow along a route. So Dijkstra's algorithm needs every edge cost to be zero or more.

A worked example on a roadmap shows the loop running. A person has taught an arm six poses. The diagram shows them, together with the time in seconds for each move that is known to be safe. The arm is at the home pose and must get to the above-chute pose as fast as possible. Each pose is labelled with its best time from home, and a blue route shows the one Dijkstra's algorithm returns.

A table tracks every turn of the loop, showing the pose taken off the list and which neighbours got a new, lower time. The answer is home, camera view, above scale, and above chute, in 4.1 seconds. The route through the bin to the scale and on to the chute came close at 4.2 seconds. The fourth turn of the loop is the one worth looking at, because the tray's time dropped from 3.8 to 3.7 seconds. This happened because a longer path in moves turned out to be a shorter path in time. Breadth-first search would have missed it, since it counts moves and not seconds.

The third method is A star, which aims at the goal. Dijkstra's algorithm spreads out evenly in every direction, because it has no idea where the goal is, so it spends effort on cells behind the start. A star fixes this with a guess about where the goal lies.

For each node, A star adds two numbers: the cost from the start to the node, which it knows, and a guess of the cost from the node to the goal. That guess is called the heuristic. So A star takes off the open list the node with the smallest total of the two numbers, rather than the smallest cost so far.

On a grid with four neighbours, a good guess is the Manhattan distance, which is the number of steps across plus the number of steps up or down, ignoring obstacles. From the start to the goal that is thirteen across and one down, so the guess is fourteen steps. However, the real path is twenty steps, because it has to go round the box.

The guess must never be more than the real cost, and a guess with that property is called admissible. With an admissible guess A star still finds the lowest-cost path. The Manhattan distance is admissible here, because an obstacle can only ever make the real path longer than the guess.

The next diagram runs both methods on the same grid, with every step costing one. The shaded cells are the ones each method took off its list. Both methods find a twenty-step path. Dijkstra's algorithm took ninety-eight cells off its list, the same as breadth-first search, because with equal costs the two behave alike. A star took off only forty-two, because the guess kept it heading towards the goal, and on a larger grid that saving grows.

The count depends a little on how ties are broken, which is what the search does when two cells have the same total. This code breaks ties by taking the cell with the smaller guess first, which is a common choice.

The costs so far have been steps and seconds, but a cost can be anything at all that the route should keep low. A common choice on an arm is clearance. This means a route that passes right next to an object is still allowed, but it counts as worse than one that keeps away from it.

In the next diagram, a move into a pink cell costs five instead of one. A pink cell is a free cell that touches an occupied one, even at a corner. On the left is the breadth-first path, which is twenty steps long, but fifteen of its cells are pink, so its cost is eighty. It hugs the obstacles. On the right is Dijkstra's path with the clearance cost, which is twenty-two steps long and costs only thirty-eight. This is because only four of its cells are pink. Those four are where it has to pass through the gap between the box and the tray. A star with the same costs found a path of the same cost, thirty-eight, and it took seventy-two cells off its list against eighty for Dijkstra's algorithm.

The two extra steps buy a path that keeps five centimetres from everything nearly all the way. This is the same trade described as padding in the planning scene on the page about planning a path, except that it is done here as a cost instead of as a hard rule.

The section ends with the pseudocode. One piece of code covers all three methods. They all start by setting the cost to zero for the start node, and putting it on the open list. Then a loop runs while the open list is not empty. The only difference is how the next node is chosen. Breadth-first search takes the node that was added first. Dijkstra takes the node with the smallest cost so far. A star takes the node with the smallest cost so far plus the guess to the goal.

If the chosen node was already finished, it skips it and goes round again. Otherwise, it marks it as finished. If it is the goal, it follows the path backwards and returns it. If not, it looks at each free neighbour. It calculates the new cost, which is the cost so far plus the move cost. If the neighbour has no cost yet, or the new cost is less than its current cost, it updates the neighbour's cost, remembers where it came from, and puts it on the open list. If the loop finishes without finding the goal, it returns that there is no path.

The step to skip a node matters for Dijkstra's algorithm and A star. This is because a node can be put on the open list more than once, each time with a lower cost. Only the first copy to come off counts. So every later copy is thrown away.

The fourth section explains where graph search is used on a robot arm. The three methods above are general, so the useful question is where an arm actually meets them. Graph search works best when the space has few dimensions or when the graph is small, and these are the places it turns up around an arm.

First, choosing a sequence of taught moves. A cell with a handful of taught poses can hold them as a roadmap, and Dijkstra's algorithm then finds the fastest sequence of known-safe moves between any two poses. The answer is the same every run, which matters in a cell that has to be signed off.

Second, answering a query on a probabilistic roadmap. A planner builds a graph of random free configurations, so to plan a move it joins the start and goal to that graph and runs Dijkstra's algorithm or A star.

Third, moving a tool across a table. When a tool moves at a fixed height, the table seen from above is a two-dimensional grid. A depth camera gives the height of each cell, so a cell counts as occupied when something in it is taller than the tool's height. A star then finds the push path across the free cells.

Fourth, moving the gripper through a voxel grid. A voxel is a cell in 3D, which is a small cube, and a depth camera's points can fill a voxel grid of a bin or shelf. A star can then plan a route for the gripper's position through the free voxels. Inverse kinematics must afterwards find joint angles for each point, and a separate check must make sure the rest of the arm does not hit anything.

Fifth, moving a mobile base under an arm. An arm on a wheeled base first needs the base to drive to the table, so base navigation plans on a flat grid of the floor, and Dijkstra's algorithm and A star are the standard tools there.

Sixth, searching joint space for an arm with few joints. For two or three joints the whole configuration space fits in a grid, and A star then gives the shortest path on that grid and gives the same answer every time.

Finally, planning the order of a task. Each state of a task can be a node, and each action an edge, so breadth-first search then finds the fewest actions from the start state to the goal state. When the question is only which object must be moved before which, a much cheaper method answers it, which is topological sort.

The fifth section covers where it is useful, and where it is not. Those uses all lean on one strength, which is that graph search is exact on the graph you give it. If a path exists on that graph it finds it, and if none exists it says so, which a random planner cannot do. So its weak points come from the graph you built rather than from the search that runs on it.

The page lists common problems, the signs you would see, and what people use instead. If there are too many cells, the search runs out of memory or takes minutes, so people use a sampling-based planner instead. If the grid is too coarse, a narrow gap fills up and the search says there is no path, so people use a finer grid near the gap or a sampler. Four-neighbour moves give a staircase path where the tool zig-zags, so people use eight neighbours, any-angle search, or a smoothing step. If the map changes while the arm moves, the path might run through a blocked place, so people search again each cycle or use an incremental method that reuses the last search.

If the guess is poor, A star is no faster than Dijkstra's algorithm, so you need a guess closer to the true cost. If the guess is more than the true cost, A star is fast but the path is not the shortest, so you must keep the guess admissible or accept the loss on purpose. If the graph only checks the gripper, the elbow might hit the shelf, so you must check the whole arm at each point or plan in joint space. Finally, if there are negative costs, Dijkstra's algorithm returns a wrong answer, so you must keep all costs zero or more, adding a constant if needed.

The problem about the guess being too large deserves one more sentence, because making the guess too large on purpose has a name of its own. Multiplying an admissible guess by a number above one is called weighted A star. This trades a slightly longer path for a much faster search, which is often worth it. The point is to make that trade knowingly rather than by accident.

The sixth section lists libraries that provide graph search. Because those weak points come from the graph rather than from the code, you rarely need to write graph search yourself, though it is a good exercise. For Python, NetworkX is the easiest to start with, providing shortest path, Dijkstra, A star, and breadth-first search functions, though it can be slow on very large grids. SciPy works on a sparse matrix of edge costs and is fast. Scikit-image finds the cheapest path directly on an image or cost grid. For C++, the Boost Graph Library is the standard choice. The Open Motion Planning Library runs a graph search on its roadmap for every query in both C++ and Python. Finally, in ROS 2, Nav2 provides grid planners for a mobile base, though not for the arm's joints.

The seventh section asks why you should choose graph search, and what it costs. Graph search is a loop that grows out from the start, taking the cheapest node next, until it reaches the goal. It gives you the best route on the graph you built, and it gives the same route every run. It also tells you for certain when no route at all exists on that graph.

The obvious alternative for an arm is a sampling-based planner. A sampler copes with six or seven joints where a grid is hopeless. However, a sampler gives a different path each run, and the path has detours. When it fails it also cannot tell you whether no path exists or it simply ran out of time. So choose graph search when the space is small enough to cut into cells, or when you already have a small roadmap of safe moves. Choose a sampler instead when the arm has many joints and the space is too big to cover.

A second alternative is to teach every path by hand, which gives the same answer every run. However, a taught path does not adapt when an object moves. Graph search on a roadmap of taught poses keeps most of that determinism and still chooses the route at run time.

Against those strengths stand three costs. First, you must build the graph yourself, which means choosing the cell size, filling in which cells are occupied, and deciding what each move costs. Second, a small cell size gives a better path but uses more memory and more time. The number of cells also grows very fast with the number of dimensions. This is the reason samplers exist. Third, the path on a grid is only as smooth as the grid itself, so it usually needs a smoothing step before an arm follows it.

The eighth section introduces a way to do things in the right order, called topological sort. The searches above find a route from a start to a goal. However, some robot problems ask a different question about a graph: in what order must these jobs be done, when some jobs must come before others?

Clearing a cluttered table is the usual example on an arm. A book lying on a box must come off before the box can be lifted, and a bottle standing in front of a cup must be moved before the gripper can reach the cup.

The answer is called a topological sort, which is a list of all the nodes in which every arrow points forwards. This means each job comes after every job it depends on.

To run that algorithm you first need the graph, and on a table each object is a node. An arrow from one object to another means the first must be moved before the second. On a table such an arrow comes from one of two facts. Either the first object rests on the second, so lifting the second first would drop or spill the first. Or, the first object is in the way of the second, so the gripper cannot reach the second while the first stands in its path.

A graph whose edges have a direction, like these arrows, is called a directed graph. A diagram shows a small table with a book on a box on a tray, a cup on the tray, and a bottle in front of the cup. There are four arrows in it. The book rests on the box, the box and the cup rest on the tray, and the bottle is in the way of the cup. However, nothing says whether the book or the bottle should go first, so either order is fine for those two.

With the graph drawn, the standard way to read an order out of it is Kahn's algorithm, published by Arthur Kahn in 1962. It works by counting, so for each node you count the arrows coming into it, and that count is called its in-degree. A node with an in-degree of zero has nothing left that must come before it, so it is ready.

The steps are as follows. First, count the arrows coming into every node. Second, put every node with a count of zero on a list of ready nodes. Third, take one node off the ready list, and add it to the order. Fourth, for each arrow going out of that node, take one off the count of the node it points to. If a count reaches zero, put that node on the ready list. Fifth, repeat from the third step until the ready list is empty. Finally, if every node is in the order, the order is the answer. If some nodes are left out, there is no valid order, because those nodes are waiting on each other.

A table tracks a run of this algorithm on the objects just mentioned. At the start, the book and bottle have a count of zero, so they are ready. The algorithm takes the book, which lowers the box's count to zero, making the box ready. Then it takes the bottle, making the cup ready. Then the box, then the cup, which lowers the tray's count to zero. Finally, it takes the tray. The order is book, bottle, box, cup, tray, and every arrow points forwards in that list, so every "before" is kept.

The ready list often holds more than one node, and at the start the book and the bottle were both ready. Which one you take does not change whether the algorithm succeeds, because it only changes which valid order you get. So a robot can spend that free choice on something else, such as taking the nearest ready object to save travel.

The work grows with the number of nodes plus the number of arrows, so for five objects and four arrows that is nine small steps. Trying every order instead would mean up to one hundred and twenty orders, and for twelve objects it would be nearly four hundred and eighty million.

The algorithm allows for nodes that are left over at the end, and the reason they are left over is always the same. A cycle, or loop, is a chain of arrows that comes back to where it started. If the graph has one then no valid order exists. This is because every node on the loop must come after another node on the loop, so none of them can go first.

Kahn's algorithm finds this without any extra work, because it simply runs out of ready nodes while some nodes are still left. A diagram shows the classic case on a table: two plates leaning against each other, with a block resting on top of both and a mug underneath. Each plate leans on the other, so each must be moved before the other, which is a loop of two arrows. The block rests on both plates, and both plates are in the way of the mug. Kahn's algorithm takes the block, because it has no arrows coming in. After that, the counts drop to one for each plate, and two for the mug. Then the ready list is empty and three nodes are left.

Not all of the left-over nodes are on the loop, because the mug is stuck only while it waits on the plates. To find the loop itself, start at any left-over node and keep stepping backwards along an arrow to another left-over node. Starting at the mug you step back to plate A, then back to plate B, then back to plate A, which has been visited already. So the loop is plate A and plate B. Knowing the loop tells the robot what to do, because no order of simple picks can clear this table. Instead, the robot needs a different kind of action for the plates, such as holding one while lifting the other, or sliding one flat first.

The pseudocode for topological sort counts the incoming arrows, builds the ready list, and loops through it, subtracting one from the target of each outgoing arrow. If it finishes and nodes are left over, it runs a loop-finding step that walks backwards through the remaining nodes until it hits a node it has already seen. This always finds a next node, because every node left over still has a count above zero, so it still has an arrow coming in from another left-over node.

Topological sort turns up wherever an arm must do several things in an order that the scene itself decides rather than the programmer. For clearing a table or a bin, the arrows come from "rests on" and "in the way", so the order the sort returns is the picking order. For building a stack or an assembly, the same graph read backwards gives the building order. For taking apart a kit or a product, screws come out before the cover, and the cover before the board, and each of those facts is an arrow. For ordering the steps of a task, you must open the drawer before reaching into it, and close the gripper before lifting, so a task planner can check a list of steps this way before running it. It is also used in building a robot's software, where the build tool compiles each package after the packages it depends on.

Topological sort is exact and fast, so it fails only when the graph is wrong or when order is not the whole problem. If an arrow is missing, the order seems valid but an object falls or the gripper collides, so you must build arrows from a conservative test with a margin round each gripper path. If the graph has a loop, the algorithm stops with objects left over, so you must find the loop and use a different action. If moving one object changes the others, the order was valid for the scene before the first pick, not after, so you must look again after each pick and rebuild the graph. If objects must go to places that are themselves occupied, there is no loop yet no order of picks works, so you must treat it as rearrangement with buffer space. Finally, if several valid orders differ greatly in travel, the order is correct but slow, so you can break ties by distance or search over the valid orders for the shortest.

You do not have to write any of this yourself, because Python's standard library already has it. The graphlib module provides a topological sorter, which takes a map from each node to the nodes it depends on and returns an order. It raises an error when there is no valid order, and the error carries the loop it found. NetworkX also provides topological sort and cycle-finding functions. In C++, the Boost Graph Library provides topological sort, which reports a loop by throwing an error.

The obvious alternative is to try orders until one works, or to use a simple rule such as taking the nearest object first. Trying orders costs a factorial number of tries. A simple rule costs nothing, but it can give an order that drops an object, and it cannot tell you when no order exists. Topological sort costs only the work of building the arrows, and in return it gives a valid order whenever one exists, or proves that none does.

The ninth section looks at the learned alternative. Everything above is written by hand, so the question is what a learned model would do in its place. A learned route planner guesses a route for the arm directly from a point cloud, in about the same time every run. It is built for large joint spaces where a grid is hopeless. However, in the small spaces and roadmaps this page is for, graph search is already fast. Graph search also gives what no network gives: the best route on its graph, the same route every run, and a certain "no route" when there is none. This is why a learned planner's answer is still checked by an ordinary planner. For the order of a task, a language model as planner chooses the steps from a request in plain words, which suits requests that change every day. For a task that stays the same, a search or a topological sort is free and fast, and it gives the same valid order every time.
